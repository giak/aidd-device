## 1. Le défaut, mesuré

Le run `06-test` a rendu `9 passed`, `exit 0` : la suite **s'exécute**. Rien n'a été injecté, donc
rien ne dit qu'elle **détecte** une régression. `9 passed` est un code de sortie, pas une morsure.

Le harnais n'a aucune commande qui exécute un produit hors du client, et le reçu ne porte aucun
champ de vérification : `run.mjs` s'arrête à `freeze|preflight|collect|faits|receipt|compare|texte`.

## 2. Périmètre

**Dans cette spec :**

- un bloc `verification` et un bloc `mutations` dans l'attendu d'un cas ;
- une commande `verifier` dans `run.mjs`, qui écrit `verification.json` et **refuse** un mutant
  survivant ;
- la lecture de cette pièce par `receipt`, qui refuse `conforme` quand le test ne mord pas ;
- l'appel de `verifier` par `fin` avant le reçu, quand le cas le déclare ;
- le contrôle 289 du banc.

**Hors de cette spec :** la campagne de mutants générés (seuls des mutants déclarés à la main sont
lus), le réseau coupé, la couverture, le seuil agrégé de 80 % / 90 %, et la correction du skill
`06-test` (spec de framework séparée).

## 3. Le schéma du cas

L'attendu, et lui seul, déclare la vérification. Aucun champ nouveau n'entre dans le gel : le gel
hache les fichiers du cas, il n'interprète pas l'attendu (`receipt` lit déjà le budget ainsi).

```json
{
  "verification": {
    "commande": "python3 -m pytest -q test_skill_analysis.py",
    "attendu_code": 0,
    "delai_ms": 120000
  },
  "mutations": [
    {
      "id": "M1",
      "fichier": "analysis.py",
      "cherche": "return frame[:duration]",
      "remplace": "return frame",
      "doit_echouer": true
    }
  ]
}
```

Règles de forme, toutes refusées si elles ne tiennent pas :

- `verification.commande` : chaîne non vide, exécutée par `bash -lc` dans la copie ;
- `verification.attendu_code` : entier, défaut `0` ;
- `verification.delai_ms` : entier positif, défaut `120000`, plafond `600000` ;
- `mutations` : liste, facultative ; quand elle est présente, elle est non vide ;
- `mutations[].id` : chaîne non vide, unique dans la liste ;
- `mutations[].fichier` : chemin relatif non vide, qui reste sous la copie du terrain ; un lien
  symbolique est refusé ;
- `mutations[].cherche` : chaîne non vide, présente **exactement une fois** dans le fichier ;
- `mutations[].remplace` : chaîne, vide permise ;
- `mutations[].doit_echouer` : strictement `true` ; un mutant qui doit survivre n'éprouve pas un test.

Un cas sans `verification` reste lisible : `verifier` refuse de le jouer, et `receipt` ne demande
aucune pièce.

## 4. `verifier` — ce qu'elle fait

```
node docs/device/harness/run.mjs verifier --run <dir> --case <id> [--cases <dir>]
```

Elle lit `<run>/faits.json` pour `repertoire_de_travail` et `<run>/raw/<cas>/manifest.json` pour le
produit collecté. Un `faits.json` absent, un répertoire de travail qui ne résout pas, un produit
collecté absent ou vide (`fichiers: []`) sont des refus : il n'y a rien à vérifier.

Elle construit un dossier jetable sous `$TMPDIR` (`aidd-verif-*`) :

1. copie du terrain, sans `.git`, `node_modules`, `__pycache__`, `.pytest_cache`, `.scratch` ;
2. copie du produit collecté par-dessus, sans `manifest.json` : c'est **le produit du run**, pas une
   retouche ultérieure du terrain, qui est éprouvé ;
3. `HOME` et les quatre `XDG_*` pointent sous le dossier jetable ; le reste de l'environnement est
   hérité ;
4. la commande est lancée avec `cwd` = la copie, `timeout = delai_ms`.

**Référence.** La commande rend `attendu_code`. Sinon `verifier` écrit `verification.json` avec
`baseline.code`, `mord: false`, nomme le code obtenu et refuse. Une référence qui échoue ne se
compare à aucun mutant.

**Chaque mutant.** Une copie neuve de la référence, le remplacement exact une fois, puis la même
commande :

- code ≠ `attendu_code` => `mord: true` ;
- code = `attendu_code` => `mord: false`, mutant **survivant** ;
- délai dépassé ou lancement impossible => `mord: false`, `delai_depasse: true` ou `erreur`, compté
  dans `mutants_non_evalues`, jamais dans `mutants_survivants`.

`verification.json` porte :

```json
{
  "cas": "<id>",
  "commande": "…",
  "attendu_code": 0,
  "delai_ms": 120000,
  "manifeste_sha256": "<sha256 du manifeste du produit collecté>",
  "baseline": { "code": 0, "duree_ms": 1234 },
  "mutations": [
    { "id": "M1", "fichier": "analysis.py", "code": 1, "mord": true, "duree_ms": 812,
      "delai_depasse": false }
  ],
  "mord": true,
  "mutants_survivants": [],
  "mutants_non_evalues": [],
  "verifie_le": "<iso>",
  "terrain": "<chemin absolu>",
  "produit": "<run>/raw/<cas>"
}
```

`manifeste_sha256` rattache la vérification au produit collecté : le reçu le recalcule et refuse une
pièce écrite sur un autre produit. `mord` n'est `true` que si la référence passe **et** toutes les
mutations déclarées mordent (liste vide : `mord: null`). `verifier` sort `0` seulement dans ce cas ; un mutant survivant, un mutant non
évalué ou une référence rouge sortent `1`, avec `REFUS —` qui nomme le mutant et le fichier. Une
mutation dont `cherche` est absent ou multiple est un refus de la **déclaration**, pas un survivant :
elle est refusée avant la course, et aucun `verification.json` n'est écrit.

`verification.json` déjà présent est refusé : une vérification ne se réécrit pas, comme un reçu.

## 5. `receipt` et `fin`

**`receipt`** : si l'attendu déclare `verification` ou `mutations`, il exige `verification.json`, le
hache, et ajoute au reçu `verification{chemin, sha256, cas, commande, attendu_code, delai_ms,
baseline{code, duree_ms}, mutations[{id, fichier, code, mord, duree_ms, delai_depasse}], mord,
mutants_survivants, mutants_non_evalues, verifie_le}`. Il refuse :

- une pièce absente (« lancer `verifier` d'abord »), d'un autre cas, ou d'une autre commande ;
- `mord: false` quand des mutations sont déclarées, **si le verdict demandé est `conforme`** : un test
  qui ne mord pas ne peut pas rendre le produit conforme ; `ecart` et `non concluant` restent
  possibles, et le reçu porte la limite ;
- une baseline dont le code n'est pas `attendu_code`.

Le reçu ajoute toujours une limite : la commande est déclarée par le cas, elle tourne sur une copie,
le réseau n'est pas coupé, et les mutations ne couvrent pas toutes les fautes (ADR-087).

**`fin`** : quand l'attendu déclare la vérification, `fin` joue `verifier` **avant** le reçu à blanc.
Un refus de `verifier` qui a écrit `verification.json` n'arrête pas `fin` : le test qui ne mord pas est
un résultat à juger (`ecart`), pas un run à cacher. Un refus sans pièce arrête `fin`. Le bloc d'étape
passe à trois étapes (`verifier`, reçu, output) quand la vérification est déclarée, à deux sinon.

**`compare`** recopie `verification` du reçu dans `output.json`, ou `null` quand le reçu n'en porte
pas : le juge lit une pièce, il ne relit pas le terrain.

## 6. Le contrôle 289

Une fixture hors dépôt, sous `$B`, avec un terrain qui porte `source.py` et deux scripts :

- `test-faux.sh` sort `0` quoi qu'il arrive ;
- `test-vrai.sh` sort `0` seulement si `source.py` contient `valeur = 1`.

Trois cas :

1. **survivant** : `test-faux.sh`, mutation `valeur = 1` → `valeur = 2` ; `verifier` sort `1`,
   `verification.json` porte `mord: false`, `mutants_survivants: ["M1"]`, et le refus nomme `M1` ;
2. **tué** : `test-vrai.sh`, même mutation ; `verifier` sort `0`, `mord: true`,
   `mutants_survivants: []` ;
3. **déclaration invalide** : `cherche` absent ; `verifier` sort `1`, nomme l'absence, n'écrit aucune
   pièce.

Le contrôle exige les trois : un `verifier` qui refuserait toujours ne passerait pas le 2 ; un
`verifier` qui accepterait toujours ne passerait pas le 1.

## 7. Critères d'acceptation

- `node docs/device/harness/run.mjs verifier` sur la fixture 1 sort `1` et nomme `M1` ;
- sur la fixture 2 sort `0` et `verification.json.mord === true` ;
- sur la fixture 3 sort `1` et ne laisse pas de `verification.json` ;
- un `receipt` qui déclare une vérification sans pièce refuse, et un `receipt --verdict conforme`
  avec `mord: false` refuse ;
- le banc rend **282/282 PASS** (`281` existants + le `289`) ;
- `node docs/device/harness/liens.mjs` rend `0` lien mort.

Le contrôle 289 éprouve les deux : la première partie `verifier` sur la fixture simple, la seconde le
reçu sur une fixture complète (gel, porte, produit neuf, trace, faits) — `receipt --verdict conforme`
refuse `mord: false`, `receipt --verdict « non concluant »` écrit et porte la pièce et ses deux empreintes.
Le chemin `fin` qui appelle `verifier` avant le reçu n'est pas joué par le banc : c'est une limite de
preuve dite au §8, pas une propriété acquise.

## 8. Limites, et ce qui rendrait cette spec fausse

- Le réseau n'est pas coupé : la commande déclarée peut l'utiliser. C'est une limite dite, pas une
  propriété.
- Les mutants sont choisis à la main : tuer `M1` ne prouve pas que la suite couvre le produit, seule
  une campagne générée le dirait (hors périmètre).
- La commande est celle du cas gelé, donc de confiance ; `verifier` ne juge pas son contenu.
- La copie du terrain peut inclure des fichiers non produits, et un test peut les lire : la
  vérification n'est pas un isolement de session, seulement un isolement de répertoire.
- Le chemin `fin` qui appelle `verifier` n'est pas joué par le banc ; le reçu et `verifier` le sont.
- Cette spec serait fausse si un `verification.json` pouvait être écrit sans que la commande ait
  tourné, ou si `receipt` acceptait `conforme` avec `mord: false`.

## 9. ADR réservée

**ADR-087** — le produit d'un skill qui écrit des tests se vérifie par mutation, et un mutant
survivant interdit `conforme`. Le reçu cite `verification.json` par son `sha256`, et la limite dit ce
que la commande ne prouve pas.
