# Spec — les traces vérifiables, lues dans la lecture déclarée

> V0.1, 2026-10-22, née à **22:12:07** (`stat -c %w`). Source : [ADR-073](../../../DECISIONS.md)
> (le raisonnement se juge sur ses traces), [brainstorm du 22 octobre](../../../brainstorm/2026-10-22-210512-processus-de-test-skill-10-task.md)
> étapes 6 et 7, et l'existant [resultat.mjs](../../../device/harness/resultat.mjs), qui lit déjà
> `CASES/<cas>.lecture.json` depuis l'[ADR-061](../../../DECISIONS.md). Cette spec est l'implémentation de
> l'intention de l'ADR-073 ; elle en corrige un point de forme, pas le principe.

## 1. Le défaut, mesuré

L'ADR-073 a nommé un bloc `attendu_details.traces[]`. Ce bloc n'existe nulle part :

- `grep -n '"traces"' docs/device/CASES/*.expected.json` ne rend rien ; les cinq attendus présents au
  moment de la mesure (quatre gelés dans le dépôt, plus `2026-10-22-211800`, non commité) portent
  `attendu_details.ordre`, une liste d'objets `{rang, geste, preuve}` ;
- `CASES/<cas>.lecture.json` porte déjà `gestes[].assertions`, lu par `resultat.mjs` et vérifié par
  `verifierLecture` ; ses types sont `trace_outil`, `falsificateur_vide`, `produit`, `pause` ;
- `resultat.mjs` ne garde de la trace que les parts `kind: "tool"`. Un texte assistant qui énonce une
  décision, ou une question en texte, n'entre dans aucune mesure de la page.

Ajouter `traces[]` créerait donc une troisième structure pour le même couple `geste`/`preuve`, après
`attendu_details.ordre` et `lecture.json`. C'est le doublon que la règle du dépôt refuse.

## 2. Décision : pas de `traces[]`, une lecture étendue

- `attendu_details.ordre` reste la **promesse gelée**, en prose : ce que le cas attend, dans l'ordre.
  Y ajouter des assertions obligerait à re-geler chaque cas et ferait entrer la lecture dans le gel.
- `CASES/<cas>.lecture.json` reste la **lecture déclarée** : la traduction machine de cette promesse,
  hors du gel, comme l'[ADR-032](../../../DECISIONS.md) et l'[ADR-061](../../../DECISIONS.md) l'ont
  établi. Une lecture réécrite après coup est visible dans l'historique git du fichier de lecture ; elle
  ne change aucun verdict.
- Aucun bloc `traces[]` n'est créé. Le principe de l'ADR-073, « on ne juge que ce que la trace laisse »,
  s'applique à la lecture existante, qui gagne deux extensions.
- La lecture ne change aucun verdict : `receipt.json` et `output.json` restent les seules pièces qui
  décident. Une lecture réécrite après le run change la page, jamais le reçu ni l'output.
- Le **cas** est l'adaptateur : il déclare ses produits, ses traces et ses falsificateurs. Le harnais ne
  connaît ni `10-task`, ni un plan, ni un rapport, ni un schéma de données ; il ne lit que les primitives
  ci-dessous. Un skill qui produit du JSON, du code ou un jeu de données n'ajoute pas un type au harnais :
  il écrit ses assertions dans son `lecture.json` et son attendu dans son `expected.json`.

## 3. Les deux extensions

Les exemples qui suivent viennent de `10-task` ; les types sont génériques : un texte, un outil, un
fichier. Aucun nom de section ou de format n'entre dans la règle.

### 3.1 `trace_texte`, pour une question ou une décision

Une assertion de type `trace_texte` :

```json
{ "type": "trace_texte", "role": "assistant", "contient": "je propose de", "a_partir_du_tour": 12 }
```

Pour une question en texte, la même assertion porte `finit_par` à la place de `contient` :

```json
{ "type": "trace_texte", "role": "assistant", "finit_par": "?", "a_partir_du_tour": 12 }
```

Règles :

- `role` vaut `assistant` ou `user`, défaut `assistant` ;
- `contient` et `finit_par` sont exclusifs : une assertion porte l'un ou l'autre, jamais les deux, jamais
  aucun ; chacun est une chaîne non vide ;
- `contient` est une sous-chaîne littérale, sensible à la casse ; ce n'est pas une expression régulière ;
- `finit_par` compare la dernière ligne non vide du texte, après suppression des espaces de fin, et
  ignore les lignes d'un bloc de code entre deux ``` ; la règle est celle d'`ouvrir`
  ([ADR-072](../../../DECISIONS.md)) ;
- `a_partir_du_tour` est un entier strictement positif optionnel, inclusif : seul un texte dont le
  numéro de tour (`seq` dans le fil) est supérieur ou égal est examiné ;
- une part qui commence par `<system-reminder>`, espaces de début ignorés, n'est jamais un texte du
  modèle, pour aucun des deux critères ;
- `lireParts` rend une seconde liste, `textes`, des parts `kind: "text"` dont `text` est une chaîne ;
  chaque entrée porte `seq`, `role`, `text` et `ts` ; `parts` reste la liste des outils, donc aucun
  consommateur existant ne voit la nouvelle liste ;
- une part `reasoning` n'est jamais lue : le type ne lit que `kind: "text"`, et une décision doit être
  énoncée dans un texte, pas dans un raisonnement exporté.

La règle de la dernière ligne hors bloc est **copiée à l'identique** depuis `ouvrir` : le banc la
compare aux mêmes trois textes (une question, un `?` dans un bloc, un rappel système) pour qu'une copie
ne dérive pas en silence.

### 3.2 `commande_contient`, pour un accès par le shell

`trace_outil` accepte un champ optionnel `commande_contient`, une chaîne non vide, sous-chaîne littérale
de la commande d'une part `tool` retenue par l'assertion. Quand il est présent, la part doit porter une
`commande` qui le contient. Si `chemin_contient` et `commande_contient` sont tous deux présents, les
deux doivent tenir. Sans le champ, le comportement actuel ne change pas.

`commande_contient` est sensible à la casse. Une part `tool` sans `commande` n'est pas une violation :
la commande n'a pas été exportée, donc la mesure manque et l'assertion rend `non observé`. Dès qu'une
part lisible porte une autre commande, l'assertion rend `violé` ; `non observé` seulement si aucune
commande n'est lisible.

Quand plusieurs critères sont déclarés, un critère contredit rend `violé`, même si un autre manque ;
`non observé` seulement si aucun n'est contredit et qu'au moins un manque.

C'est ce qui permet de déclarer « la session a lancé `rg` sur le README » sans confondre cette lecture
avec un chemin d'outil que la part shell ne porte pas.

## 4. Ce que la page en fait

`RESULTAT.md` garde son tableau à trois colonnes, `geste | détail | état`. Le détail gagne la preuve
observée :

- une assertion `trace_texte` tenue dit le tour et la valeur de `contient`, bornée à 60 caractères,
  par exemple `texte du tour 12 : « … je propose de … »` ; l'extrait est la chaîne déclarée, jamais le
  texte entier, et il est échappé pour la cellule ; s'il porte un mot interdit par la page (`seq`,
  `morsure`), `verifierContrat` refuse le fichier au lieu de le recopier ;
- une assertion `trace_outil` avec `commande_contient` dit `commande du tour 12 : « rg README »`,
  avec la valeur de `commande_contient`, bornée à 60 caractères, jamais la commande entière ;
- trois états, jamais deux : trace absente, ou aucune partie examinable, se dit `non observé` ; une
  partie examinable qui ne satisfait pas le critère se dit `violé` ; une partie qui le satisfait se dit
  `tenu` ; jamais `tenu` sans preuve citée.

Les trois états et le plafond de 80 lignes de l'[ADR-061](../../../DECISIONS.md) ne changent pas.
Aucune section n'est ajoutée.

## 5. Ce que le reçu et le verdict ne font pas

- `receipt.json` ne gagne aucune clé `traces`. Les mesures du run restent celles du §7 de
  [ARCHITECTURE](../../../ARCHITECTURE.md).
- `output.json` ne change pas : le juge lit toujours le reçu, la trace et l'attendu gelé.
- Une lecture `lecture.json` réécrite après coup ne change ni le reçu ni l'output ; c'est la limite déjà
  dite par l'ADR-061. La page est une lecture, pas une attestation.
- Une assertion `trace_texte` ne prouve pas une pensée : elle constate un texte émis. Une question
  rhétorique qui finit par `?` reste un texte, et la spec ne prétend pas la comprendre.
- Le contenu spécifique (un message, un JSON, du code, un rapport, un jeu de données) n'est pas validé
  par `resultat.mjs` : le cas le décrit dans `attendu`, le juge le lit, et la page cite le geste et le
  chemin ou le tour. Le protocole ne gagne pas un schéma par format ; ce serait une dette par skill. Si une
  validation mécanique devient nécessaire, elle se discute comme une primitive générique, pas comme un
  type par skill.

## 7. Critère de sortie

- `bash docs/device/harness/banc-harnais.sh` rend **262/262 PASS**, `exit 0`, `0` `FAIL`.
- `node --check` sur `resultat.mjs` et `orchestrer.mjs`, `bash -n` sur `banc-harnais.sh`,
  `liens.mjs` et `git diff --check` restent à `0`.
- Sur une copie d'un run réel, avec un `lecture.json` qui déclare deux gestes, une décision et une
  question en texte : `RESULTAT.md` porte les deux lignes, chacune avec son état et sa preuve, ou
  `non observé` ; aucune ligne `tenu` sans preuve ; le corps n'emploie ni `seq`, ni `morsure`, ni
  `falsificateur`.
- Une assertion dont la trace manque, ou dont la trace ne porte aucune partie examinable, rend
  `non observé`, jamais `tenu` ; une assertion dont la partie examinable ne satisfait pas le critère
  rend `violé`.

## 9. Ce que cette spec ne fait pas

- Elle ne crée aucun bloc `attendu_details.traces[]`.
- Elle ne change ni le gel, ni le reçu, ni l'output, ni un verdict.
- Elle ne juge pas le sens d'un texte : `contient` et `finit_par` sont littéraux.
- Elle ne mesure pas une intention, une motivation profonde ou un raisonnement caché.
- Elle ne teste pas l'effet d'un produit : c'est un autre run, pas une lecture de trace.
- Elle ne transforme pas `lecture.json` en pièce gelée : il reste hors du gel, comme l'ADR-032 l'exige.

## 10. Ce qui rendrait cette spec fausse

Si un `?` dans un bloc de code rend `tenu`, la règle de `finit_par` est fausse. Si une trace absente rend
`tenu`, les trois états sont faux. Si `commande_contient` accepte une autre commande, la lecture est
fausse. Si une assertion `trace_texte` change un verdict, la séparation entre lecture et reçu est
fausse. Si `lecture.json` est servi sans `verifierLecture`, le refus des lectures mal formées est perdu.
Si le contrôle 233 n'inclut pas le nouveau type, le vocabulaire fermé est faux.
