## 1. Avant d'ouvrir la session

### 1.0 La porte : le dossier, avant l'ouverture

Le premier geste n'est pas de vérifier le gel, c'est de vérifier **où** la session va s'ouvrir : un run
dans un autre dossier écrit ailleurs, et rien de ce qu'il produira ne sera imputable au cas (§4 de la
demande). La porte tombe avant la session, là où les refus du reçu constatent après coup.

```text
node /home/giak/projects/aidd-device/docs/device/harness/run.mjs preflight \
  --case 2026-10-15-133423-promesse-memoire-avant-ecriture --texte "$W/texte-a-remettre.txt"
→ preflight ok — 2026-10-15-133423-promesse-memoire-avant-ecriture : ouverture autorisée dans
  /home/giak/projects/aidd-device-work/2026-10-15-133423-promesse-memoire-avant-ecriture/terrain
  (HEAD 416ec1f, porcelain 0 ligne(s)) ; gel 0d9a2180 re-haché, 2 fichier(s) du cas et 8 référence(s)
  ; texte 832036f7 (254 octets) conforme au §5 substitué
→ exit 0
```

Avec `--texte`, elle vérifie en plus **le texte qui va partir** : le §5 du cas, `$RACINE` substitué par
la racine du gel, sans variable et sans saut de ligne final. C'est la seconde chose que l'opérateur fait
avant d'ouvrir, et la seule dont le contenu dépend de la machine :

```bash
CAS=2026-10-15-133423-promesse-memoire-avant-ecriture
H=/home/giak/projects/aidd-device/docs/device/harness/run.mjs
RACINE=$(node -e 'console.log(require("/home/giak/projects/aidd-device/docs/device/CASES/"+process.argv[1]+".freeze.json").racine_espace_de_travail)' "$CAS")
W="$RACINE/$CAS"
T=$(sed -n '/^<<<DEMANDE$/,/^>>>DEMANDE$/p' "docs/device/CASES/$CAS.request.md" | sed '1d;$d' | sed "s|\$RACINE|$RACINE|g")
printf '%s' "$T" > "$W/texte-a-remettre.txt"     # sans saut de ligne final, comme au §2.1
node "$H" preflight --case "$CAS" --repertoire "$W/terrain" --texte "$W/texte-a-remettre.txt"
```

Sans `--repertoire`, le dossier examiné est le **répertoire courant** : se placer dans `$W/terrain` et
lancer la porte, c'est demander l'autorisation pour ce dossier-là. Elle refuse (`exit 1`) si le dossier
n'est pas celui que le gel nomme `travail`, s'il n'existe plus, s'il n'est pas un répertoire, s'il vit
dans le dépôt du dispositif, ou s'il n'est plus dans l'état gelé — `HEAD` **et** `porcelain`, parce que
la paire avant/après du §5.2 ne se lirait pas sur un autre état. Le cas est re-haché comme au reçu :
autoriser l'ouverture sur un cas qui a bougé n'autoriserait rien.

Les neuf refus, éprouvés sur banc le 2026-10-15 (voir §5) : `--repertoire` sur le terrain original, sur
`$W/framework-origin`, sur l'ancien foyer `~/runs/…`, sur le dépôt du dispositif ; arbre `travail` gelé
qui pointe dans ce dépôt ; arbre `travail` qui n'est plus un dépôt git ; arbre à la bonne révision mais
dont le `porcelain` a changé ; cas dont un fichier a bougé depuis le gel ; cas sans gel. Le reçu refait
le contrôle du dossier (§1.4) : une porte peut être sautée.

### 1.1 Que le gel tient encore

Le gel a été pris le `2026-10-15T22:11:24.782242943+0200`, avant toute ouverture de session, et
**refait** six fois le même jour, l'ancien détruit à chaque fois : après le premier scellé du cas,
après la rectification du §7 (l'empreinte `1b9a8434` ne couvrait plus le texte), après le passage aux
chemins relatifs ([ADR-016](../../../DECISIONS.md)), après la publication de l'origine
([ADR-017](../../../DECISIONS.md)), après le **déplacement** de l'espace de travail (§2, §4), puis
après le passage à la **racine déclarée** ([ADR-019](../../../DECISIONS.md)). Les deux derniers ont
**changé l'empreinte** — `38fa91f4` → `07246039` → `0d9a2180` — et c'est la même cause : la formule ne
hache ni les chemins des arbres ni ceux du gel, mais elle hache le **contenu** des fichiers du cas, et
un chemin de machine y était écrit. Il n'y en a plus : le cas nomme `$RACINE`, donc déplacer l'espace
de travail, changer de machine ou rejouer ailleurs ne réécrivent plus le cas gelé — ils redéclarent la
racine. Les quatre re-gels d'avant, eux, laissaient l'empreinte intacte.

Sa formule se recalcule **sans réécrire un chemin** : les deux fichiers du cas se lisent depuis la
racine du dépôt, les huit références depuis un checkout de l'arbre que le gel nomme. Ce checkout est
le seul paramètre qu'un tiers fournit, avec la révision gelée : les `remotes` de l'arbre disent où
le prendre.

```text
export RACINE_FRAMEWORK=/chemin/vers/votre/checkout   # « revision-sous-test » à la révision gelée
python3 - <<'PY'
import json,hashlib,os,subprocess,sys
RACINE=os.getcwd(); CAS="2026-10-15-133423-promesse-memoire-avant-ecriture"; FR=os.environ.get("RACINE_FRAMEWORK","")
if not FR: raise SystemExit("RACINE_FRAMEWORK manquant : y mettre le checkout de l'arbre gelé")
g=json.load(open(os.path.join(RACINE,"docs/device/CASES",CAS+".freeze.json")))
sha=lambda p: hashlib.sha256(open(p,"rb").read()).hexdigest(); l=[]; ok=[]
arbres={a["label"]:a for a in g["arbres"]}
for x in g["fichiers"]:
    h=sha(os.path.join(RACINE,x["chemin"])); l.append(f'{x["role"]}\t{os.path.basename(x["chemin"])}\t{h}')
    ok.append(h==x["sha256"]); print("fichier", x["role"], h==x["sha256"])
for label in sorted({r["arbre"] for r in g["references"]}):
    complet=subprocess.run(["git","-C",FR,"rev-parse","HEAD"],capture_output=True,text=True).stdout.strip()
    attendu=arbres[label].get("head_complet") or arbres[label]["head"]   # complet, ou court (préfixe)
    ok.append(complet.startswith(attendu))
    print("arbre", label, "HEAD", complet[:8], "gelé", attendu[:8], complet.startswith(attendu))
for r in g["references"]:
    h=sha(os.path.join(FR,r["chemin"])); l.append(f'reference\t{r["chemin"]}\t{h}')
    ok.append(h==r["sha256"]); print("reference", r["chemin"], h==r["sha256"])
emp=hashlib.sha256(("\n".join(sorted(l))+"\n").encode()).hexdigest()==g["empreinte"]
print("empreinte", emp)
sys.exit(0 if all(ok) and emp else 1)
PY
→ 10 fois True, l'arbre à sa révision gelée, puis empreinte True ; `exit 0` — un seul `False`
→ sort en `1`, et c'est ce code que l'opérateur regarde avant d'ouvrir. Le `HEAD` est comparé
→ **complet** (`head_complet`) : `--short` s'abrège par dépôt, le même commit rend 7 caractères
→ dans un clone et 8 ici — mesuré sur `fe48de12`/`fe48de1`
```

Où prendre ce checkout, mesuré le 2026-10-15 : les `remotes` de l'arbre `revision-sous-test` mènent à
`https://github.com/ai-driven-dev/framework.git`, où `4c39e5c5` est public — mais un `git fetch` par
`sha` y est refusé (« impossible de trouver la référence distante »), il faut un
`git clone --filter=blob:none --no-checkout` puis `git checkout 4c39e5c5`.

Les quatre `HEAD` gelés sont **publics**, chacun par la branche que le gel nomme
(`arbres[].refs_distants`) : `framework-origin` `fe48de12` sur `github.com/giak/framework`, branche
`gel/2026-10-15-fe48de12` — `git clone --branch gel/2026-10-15-fe48de12 --single-branch` la donne ;
`terrain` et `travail` `416ec1f` sur `github.com/giak/audio-sync-tool` (`main`) ; `revision-sous-test`
`4c39e5c5` sur l'upstream, où 83 branches le portent — mesuré dans un clone public, alors que le
`refs_distants` du gel reflète le miroir local des deux copies. Ce qui ne se reconstitue pas, c'est le
`porcelain` gelé : les fichiers non suivis ne sont dans aucun commit.

Un seul `False` sur un fichier du cas ou une référence rend le gel caduc : **ne pas ouvrir la
session avant de refaire le gel** (sa commande complète est dans le champ `commande` du
`.freeze.json` ; `--refreeze` détruit le précédent, et c'est la nouvelle empreinte que le reçu
portera). Le refaire depuis ailleurs n'est plus un travail de réécriture : `--ref-root` doit être
l'un des `--arbre`, et le reste du gel ne porte plus que des chemins relatifs.

### 1.3 Le répertoire du run

Nom imposé par la spec §4 : `runs/<horodatage>-<révision du framework>-<révision du dispositif>/`,
séparateurs à tirets ([ADR-023](../../../DECISIONS.md)). Sous le foyer du
dispositif, soit `docs/device/runs/` :

- la **révision du dispositif** (le v6 l'écrit `dispositif@rev`) : ce que rend la commande au moment du run — `963a5b8` au dernier relevé,
  2026-10-15. Un fichier non commité du dispositif à ce moment-là n'est pas nommé par cette
  révision : le dire dans le reçu plutôt que le taire.

Rien d'autre n'est créé dans ce répertoire par la main : `collect` y écrit `raw/<cas>/` et son
manifeste, l'opérateur y ajoute `last-message.md` et `trace/`, `receipt` y écrit `receipt.json`.

### 1.5 Où vit la trace machine, et comment on l'exporte

**Le client du second run est Freebuff** (décision du 2026-10-15, après le premier run, qui
utilisait `opencode`) : sa trace machine vit dans une base SQLite par projet,
`~/.config/freebuff-desktop/projects/<projet>-<uuid>/desktop-v2.db`, tables `threads` et `messages`.
Les trois sources constatées sur cette machine (spec §5.1) restent : Freebuff Desktop
(`desktop-v2.db`, chaque geste est une part de `parts_json`), `claude` CLI
(`~/.claude/projects/<cwd-encodé>/<session>.jsonl`), `opencode`
(`~/.local/share/opencode/opencode.db` et `storage/{session,message}`). Le harnais n'en lit
**aucune** : il ne fait que constater que `chemin_exporte` existe.

L'export de la session Freebuff : une ligne JSON par part, dans l'ordre des messages.

```text
sqlite3 -readonly ~/.config/freebuff-desktop/projects/<projet>-<uuid>/desktop-v2.db "
  select json_object('seq', m.seq, 'role', m.role, 'kind', json_extract(value,'$.kind'),
                     'open', json_extract(value,'$.open'), 'text', json_extract(value,'$.text'),
                     'ts', m.ts)
    from messages m, json_each(m.parts_json)
   where m.thread_id='<thread>' order by m.seq, json_each.key;" > "$RUN/trace/echange.jsonl"
```

Éprouvé le 2026-10-15 sur ce poste : 533 lignes pour une session d'audit, une par part, les genres
rencontrés étant `text`, `reasoning`, `tool`, `changes`, `compaction` et `ad` — liste **incomplète**, pas
fausse : le relevé du 2026-10-16 (§1.7) en a montré un septième, `notice`. L'export se copie dans
`$RUN/trace/`, avec la commande qui l'a produit et la fenêtre `horodatage_debut`–`horodatage_fin`.
C'est la seule pièce que l'opérateur n'écrit pas — et celle sans laquelle le run n'est qu'une
parole.

### 1.6 Que le contexte du candidat soit mesuré, et lu dans la trace

Mesuré le 2026-10-15, après le premier run : une session peut mourir **au plafond de son contexte**, et
le serveur **tronque alors en silence** (un prompt de ~40 000 jetons rend `prompt_eval_count` =
16 386, `ollama ps` annonce `CONTEXT 32768`). Aucune pièce du run ne le montrait : ni la trace du
client, qui compte ce qu'il a *envoyé*, ni le reçu.

Le second run change de client : **la session opératrice est une session Freebuff**, à modèle hébergé.
Le plafond n'est donc plus celui du serveur local, et la mesure n'est plus une sonde mais une lecture,
faite **après** le run, dans ses propres messages :

```text
sqlite3 -readonly ~/.config/freebuff-desktop/projects/<projet>-<uuid>/desktop-v2.db "
  select m.seq, json_extract(m.metrics_json,'$.context.windowTokens'),
                json_extract(m.metrics_json,'$.context.compactionThresholdTokens'),
                json_extract(m.metrics_json,'$.context.usedTokens')
    from messages m where m.thread_id='<thread>'
     and m.metrics_json like '%windowTokens%';"
```

Relevé dans la base de Freebuff le 2026-10-15 : **la fenêtre annoncée varie d'un message à l'autre

## 3. Ce qui doit revenir

### 3.1 L'ordre, et les commandes

```text
H=/home/giak/projects/aidd-device/docs/device/harness/run.mjs

node "$H" collect --run "$RUN" --case "$CAS" --from "$W/terrain/aidd_docs"
# la session n'a rien produit (spec §9 : produit = sa sortie brute) :
node "$H" collect --run "$RUN" --case "$CAS" --sans-produit
# à la main, ensuite : raw/$CAS/last-message.md (le dernier message de la session, tel quel)
# et trace/ (l'export et la commande qui l'a produit)
node "$H" receipt --run "$RUN" --case "$CAS" --faits faits.json
# le juge, ensuite, sur le reçu SEUL :
node "$H" compare --run "$RUN" --case "$CAS" \
  --difference "<ce que le produit fait>" \
  --phrase "<au vu de l'attendu écrit, le produit fait X ; l'attendu disait Y>" \
  --verdict conforme|ecart|non concluant --limites mord|ne mord pas|non évaluable
```

1. **`collect`** copie verbatim le produit sous `raw/<cas>/` et écrit son manifeste : `sha256`,
   taille, `birth` de chaque fichier, et la source absolue. Le produit attendu est la table
   `Write to` de `references/memory-destinations.md`, donc `terrain/aidd_docs/` — tout le reste est
   hors produit (demande §6), même écrit dans le répertoire de travail.
   Il refuse : un dossier déjà collecté (deux collectes font deux produits), un lien symbolique
   (une sortie du répertoire de travail n'est pas un produit), une copie dont le `sha256` diffère,
   un `--from` vide — et, depuis l'[ADR-020](../../../DECISIONS.md), tout `--from` dont le chemin
   résolu ne tombe pas dans l'arbre que le gel nomme `travail` : un produit venu du terrain original,
   de `framework-origin` ou d'ailleurs n'est pas le produit de ce run. Le manifeste écrit l'arbre
   d'origine (`arbre_de_travail`), et le reçu refait le contrôle sur ce manifeste.
2. **`last-message.md`** s'écrit après lui, à la main : le dernier message de la session, verbatim.
3. **`trace/`** reçoit l'export du §1.5 et sa commande.
4. **`receipt`** s'écrit à chaud, pendant le run, et refuse d'écraser un reçu existant : un reçu
   reconstruit le lendemain est un témoignage, pas un reçu. Il exige le gel, le manifeste et
   `faits.json` ; il remesure les quatre arbres ; il vérifie les quatre falsificateurs du §5.
5. **`compare`** appartient au juge, pas au run : il travaille sur le reçu seul, ne voit pas la
   session, et écrit `output.json` — l'attendu, le produit brut, la différence, la phrase de
   verdict, les limites, et les attendus écartés comme non testables.

### 3.2 Les quatre falsificateurs, et ce que le harnais ne lit pas

Un seul suffit à faire tomber le run, et le verdict suit la preuve (spec §7) :

| Condition (§5) | Ce qui la fait mordre |
| --- | --- |
| 1 — naissance | le `birth` d'un fichier produit est antérieur au gel |
| 2 — trace | la trace machine ne porte aucun échange dans la fenêtre du run |
| 3 — arbre | le produit existe alors que le `porcelain` de `travail` est inchangé |
| 4 — empreinte | le produit est identique à un fichier déjà présent avant le run |

La condition 2, le harnais **ne peut pas** la lire : il l'écrit lui-même en limite (« le harnais ne
lit aucune des trois sources du §5.1 »). La pièce (1) est attestée par l'export, pas par ce script.

### 3.3 Le plafond du verdict

- naissance **et** trace **et** arbre → le cas peut être `conforme` ou `écart` ;
- trace et arbre, sans la naissance → verdict possible, la limite dite dans le reçu ;
- sans naissance ni trace → `non concluant`, quoi que dise l'opérateur ;
- cloisonnement rompu → `non concluant`, dans tous les cas.

Le reçu porte ces limites, et la phrase de verdict — « au vu de l'attendu écrit, le produit fait X ;
l'attendu disait Y » — n'attribue ni faute ni mérite : elle compare.
