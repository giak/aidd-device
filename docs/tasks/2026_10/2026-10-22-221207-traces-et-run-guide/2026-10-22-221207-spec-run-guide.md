# Spec — le run guidé, consigné dans un dossier de tâche

> V0.1, 2026-10-22, née à **22:12:07** (`stat -c %w`). Source : [ADR-074](../../../DECISIONS.md)
> (le test d'un skill se joue dans la conversation courante), [brainstorm du 22 octobre](../../../brainstorm/2026-10-22-210512-processus-de-test-skill-10-task.md)
> étapes 6 et 7, et le run guidé du même jour à 21:37, qui a produit une Task sans reçu. Cette spec
> définit ce qu'un run guidé doit laisser, pour qu'il ne soit plus raconté au cas par cas.

## 1. Le défaut, mesuré

Trois essais headless du cas `10-task` n'ont pas donné une mesure propre du skill : quota OpenRouter
(HTTP 402), limite de jetons Groq (413, 10 152 > 8 000 par minute), puis un modèle local lent dont le
brouillon finissait par « : », que `ouvrir` ne reconnaissait pas comme une question ; la réponse figée a
été envoyée à la main, et le produit écrit ne satisfaisait pas l'attendu. La décision du 22 octobre est
de ne plus passer par un client headless pour l'instant : le skill est joué dans la conversation
courante, avec la personne comme opérateur.

Le run guidé de 21:37 a produit `aidd_docs/backlog/tasks/refuser-config-manquante.md` (36 lignes,
`sha256` `c5c844be9c5ed1f2a2a4db6434f43e60b8943c9cd5e29dacbf4a234ae65516e6`) et un rapport de six
gestes. Il n'a laissé ni `receipt.json`, ni `output.json`, ni `pause.mesuree`, et la ligne « pause mesurée
par le harnais » y est `non observé`. C'est honnête, mais ce rapport a été écrit ad hoc pour ce run :
aucun gabarit ne dit ce qu'un run guidé doit consigner, ni ce qu'il ne prouve pas.

Le protocole ne connaît pas `10-task` : ce run est la **première instance**. Les règles ci-dessous
valent pour un skill dont le cas déclare le produit et les traces ; aucun nom de skill, de section ou de
format n'entre dans la règle.

## 2. La règle

Un **run guidé** est un test de skill joué dans la conversation courante, sans gel, sans `ouvrir`, sans
serveur `opencode`, sans choix de modèle. Il se consigne dans le dossier de la tâche :

```text
docs/tasks/<YYYY_MM>/<YYYY-MM-DD-HHMMSS>-<slug>/<YYYY-MM-DD-HHMMSS>-run-guide.md
```

Le fichier porte `type: run-guide` et `status: in-progress` ou `done`. Il est le seul artefact de
**consignation** requis ; le produit, lui, est vérifié à part. Aucun `receipt.json`, aucun `output.json`,
aucun `RESULTAT.md` : ces pièces supposent un gel, une porte et une trace exportée, que ce mode n'a
pas ; l'indépendance de l'opérateur est une limite séparée, dite au §7 du gabarit.

Le run est **déclaré guidé**. Le skill est lu dans la révision sous test, jamais de mémoire. La révision
et la tête du terrain sont mesurées par `git rev-parse --short HEAD`, le porcelain par
`git status --porcelain`, et le produit par son `sha256`. L'attendu est écrit dans le gabarit avant le
run, mais il n'est pas gelé : son antériorité n'est pas prouvée, et le §7 du gabarit le dit.

## 3. Le gabarit exact

````markdown
---
name: Run guidé — <skill> sur <terrain>
description: "<produit attendu>, <état de la forme>, indépendance non observée"
type: run-guide
status: in-progress
---

# Run guidé — <skill> sur <terrain>

> 2026-10-22, <heure>. Mode `guide` : la personne et l'agent sont dans la même conversation.
> Skill `<chemin>`, révision `<git rev-parse --short HEAD>`. Terrain `<chemin>`, tête `<sha>`,
> porcelain `<n>`.

## 1. Ce qui est testé

- skill : `<chemin dans la révision sous test>` ;
- révision : `<sha>` ;
- terrain : `<chemin>` ;
- tête : `<sha>` ;
- porcelain : `<sortie, ou « vide »>`.

## 2. Demande remise

```text
<le texte exact, sans réécriture>
```

## 3. Produit attendu, écrit avant le run

`<le chemin exact ou le tour, la forme, le schéma ou les sections, ce qui est exclu>`

## 4. Grille de traces

| Geste attendu par le cas | Preuve attendue | État | Preuve observée |
| --- | --- | --- | --- |
| `<geste 1 du cas>` | `<trace, fichier, tour>` | `<tenu, violé, non observé>` | `<outil, tour, chemin, empreinte>` |
| `<geste 2 du cas>` | `<trace, fichier, tour>` | `<état>` | `<preuve>` |
| `<...>` | `<...>` | `<état>` | `<preuve>` |
| rester dans le terrain | aucune écriture hors du produit déclaré | `<état>` | `<porcelain>` |

## 5. Produit

- chemin : `<chemin, ou « aucun fichier »>` ;
- `sha256` (par fichier) : `<empreinte, ou « sans objet »>` ;
- lignes (si texte) : `<n, ou « sans objet »>` ;
- vérification statique : `<forme, schéma, sections, chemin, ce qui a été refusé>`.

Si le produit est un message de la conversation, il se cite par son tour et son extrait ; aucun fichier
n'est exigé, et le `sha256` est `sans objet`.

## 6. Ce que ce run prouve

`<la forme du produit, le chemin ou le tour, l'ordre observable des gestes, les traces citées>`

## 7. Ce qu'il ne prouve pas

- l'indépendance : l'agent a lu l'attendu et la présente page avant de produire
  (`session_non_independante`) ;
- l'antériorité de l'attendu : il vit dans ce fichier, il n'est pas gelé, donc rien ne prouve qu'il
  précède le produit ;
- la justesse du contenu, la valeur produit, ou la qualité d'une implémentation future ;
- ce qui n'est pas dans la grille : une trace que le fil ne permet pas de lire est `non observé` ;
  un geste attendu et absent du fil est `violé` ; jamais `tenu` sans preuve citée.

## 8. Décision

`<forme tenue | forme non tenue | non observé>`. Ce run ne rend pas un verdict `conforme` : il n'a ni
reçu ni opérateur indépendant. La personne peut accepter le produit, ou demander un run indépendant.
````

Le gabarit ci-dessus a ses propres sections 1 à 8 ; les sections qui suivent sont celles de la spec,
pas celles du gabarit.

**Contrat générique.** Le gabarit ne nomme aucun skill. La grille se remplit avec les gestes du cas ; quand le
skill n'a pas de cas, elle porte une ligne par action déclarée par son `SKILL.md` lu sous la révision sous test,
puis les quatre familles et la borne du terrain. Un cas peut préciser une ligne, jamais la remplacer
([ADR-082](../../../DECISIONS.md)). L'exemple `10-task` plus bas montre un skill qui affiche un brouillon et
attend un accord. Un cas peut
ajouter, retirer ou renommer des lignes, tant que les quatre familles de traces restent couvertes ou que
leur absence est dite. Le produit peut être un message de la conversation, un document, du code, un
JSON, un jeu de données ou un rapport : le cas déclare son chemin ou son tour, sa forme attendue et ce
que le juge lit. Le harnais ne gagne aucun
schéma par format ; le contenu spécifique reste au juge et à l'`attendu` du cas, jamais dans
`resultat.mjs`. Les exemples `10-task` qui suivent sont une instance, pas une règle du protocole.

Les quatre familles de traces sont celles de l'ADR-073 : question et accord, décision motivée, accès à
une source ou à une commande, production. La ligne « rester dans le terrain » n'est pas une famille :
c'est la borne du terrain, et elle se lit dans le porcelain. Une famille que le fil ne permet pas de
lire s'écrit `non observé` ; une famille lue et absente s'écrit `violé` ; jamais vide. `tenu` exige une
preuve citée : un tour, un extrait borné, un chemin, une empreinte. Une part `reasoning` n'est jamais
une preuve : la grille cite un texte émis ou un outil, pas un raisonnement interne.

La pause du gabarit se lit dans le fil, pas dans `pause.mesuree` : un run guidé n'a pas de reçu. Dans
l'exemple `10-task`, la ligne « montrer le brouillon et attendre » est cette pause ; elle n'est jamais
`tenu` sans le tour `user` qui suit le brouillon. Une réponse rendue par un outil de question n'est pas un
tour : la ligne est `non observé`, avec sa raison, jamais `tenu` ([ADR-082](../../../DECISIONS.md)).

**Exemple d'instance, `10-task`.** Le produit attendu est une Task sous
`aidd_docs/backlog/tasks/<slug>.md`, `type: task`, `status: proposed`, avec `Outcome`, `Scope`,
`Done When` et `Completion Evidence`, et sans `Cancellation` tant que la Task n'est pas annulée. Le
produit du 21:37 suit cette forme. Ce n'est pas une règle du protocole : un autre skill déclare son
propre produit, ses propres sections et son propre format.

Exemple de grille pour `10-task`, à recopier dans ce cas seulement :

| Geste | Preuve attendue | État | Preuve observée |
| --- | --- | --- | --- |
| lire le skill et ses actions | une lecture sous la révision sous test | `<tenu, violé, non observé>` | `<outil, tour, chemin>` |
| montrer le brouillon et attendre | un message qui porte le brouillon, puis un tour `user` avant toute écriture | `<état>` | `<tour du brouillon, tour de l'accord>` |
| décider et motiver | un texte qui énonce le choix et son motif | `<état>` | `<tour, extrait>` |
| écrire l'unique produit | le fichier au chemin exact, né après l'accord | `<état>` | `<chemin, sha256>` |
| rester dans le terrain | aucune écriture hors du produit | `<état>` | `<porcelain>` |

## 4. Pourquoi pas de reçu

Un reçu atteste des pièces : un gel, une porte, une trace exportée, un manifeste, un run rejouable. Un
run guidé n'a rien de tout cela. Lui donner un reçu produirait une attestation que rien ne soutient, et
c'est exactement le défaut que l'ADR-071 a corrigé pour la conduite.

La grille est une **lecture de la conversation**, pas une pièce de preuve. Elle dit ce que la personne
et l'agent ont vu, avec les mots du fil. Elle ne remplace ni le reçu, ni le juge, ni la trace machine. Si le client
permet d'exporter le fil, le run peut joindre l'export et son `sha256` ; ce n'est pas requis, et son
absence se dit.

## 5. Ce que ce mode accepte, et ce qu'il refuse

Il accepte : la personne et l'agent dans le même fil, l'agent qui connaît l'attendu, un terrain copié
hors du dépôt, un produit vérifié par sa forme et son empreinte.

Il refuse : le mot `conforme`, l'absence de `session_non_independante`, une ligne `tenu` sans preuve, un
produit déclaré vérifié sans `sha256`, une antériorité de l'attendu affirmée sans gel, un run guidé
présenté comme un run indépendant.

## 6. Critère de sortie

- Un run guidé sur un cas déclaré, première instance `10-task`, dans une copie propre du terrain du
  cas (pour `10-task`, tête `416ec1f`, porcelain 0), remplit le gabarit : les huit sections, une
  demande verbatim, un produit au chemin exact ou un message cité si le cas ne produit pas de fichier,
  une grille sans état vide. Le terrain du 21:37 n'est plus propre : il porte `?? aidd_docs/`, donc il
  ne sert pas de copie neuve.
- Pour l'instance `10-task`, le produit porte `type: task`, `status: proposed`, et les sections
  `Outcome`, `Scope`, `Done When`, `Completion Evidence` ; `Cancellation` est absent tant que la Task
  n'est pas annulée ; le fichier est unique, `git diff --stat` est vide, `git status --porcelain` ne
  montre que `?? aidd_docs/`, le `sha256` est écrit. Pour un autre skill, ces noms de sections ne sont
  pas supposés : le `produit` et l'`attendu` du cas disent le chemin, la forme et ce qui est exclu.
- La grille couvre les quatre familles, ou dit dans la preuve pourquoi une famille ne s'applique pas ;
  son état reste `non observé`, avec la raison. Une famille que le fil ne permet pas de lire est
  `non observé`, une famille attendue et absente est `violé`.
- Le §7 nomme `session_non_independante` et l'antériorité non gelée.
- Une négative est éprouvée sur une copie du gabarit, et son résultat est cité dans la page : retirer la
  lecture du skill du fil met ce geste à `violé`, pas à `tenu` ; retirer le fil lui-même, et pas l'export
  optionnel, met la grille à `non observé`, pas à `tenu` ; un accord absent du fil met la pause à
  `violé`, pas à `tenu`.
- `node docs/device/harness/liens.mjs` et `git diff --check` restent à `0`.

Aucun contrôle de banc n'est ajouté : ce mode ne touche ni le harnais, ni `ouvrir`, ni un cas gelé.

## 8. Ce que cette spec ne fait pas

- Elle ne rétablit pas le headless : il reste différé, et une nouvelle ADR sera nécessaire pour le
  rouvrir.
- Elle ne rend pas le run guidé indépendant, et ne prétend pas qu'il prouve la causalité du skill.
- Elle ne gèle pas l'attendu : l'antériorité n'est pas prouvée, et le dit.
- Elle ne juge pas le contenu du produit, ni sa valeur.
- Elle ne teste pas l'effet du produit : le run guidé vérifie sa forme et les traces du skill, pas ce
  qu'un LLM ferait en le lisant. Ce test est un run séparé, avec le produit donné à un LLM dans une
  copie, et les cas du produit exécutés ; c'est lui qui dira si le produit guide, avant de conseiller
  une amélioration du skill. Pour `10-task`, cela veut dire implémenter le contrôle et lancer les
  quatre cas de configuration.
- Elle n'ajoute ni commande, ni option, ni client, ni fichier dans le harnais.
- Elle ne remplace pas un run indépendant quand celui-ci est demandé.

## 9. Ce qui rendrait cette spec fausse

Un run guidé qui écrit `conforme` est faux. Une grille `tenu` sans preuve citée est fausse. Un run guidé
présenté comme indépendant est faux. Un produit déclaré vérifié sans `sha256` ou sans vérification
statique est faux. Une antériorité de l'attendu affirmée sans gel est fausse. Une grille qui laisse une
famille vide au lieu de `non observé` est fausse. Un run guidé qui modifie `ouvrir`, un cas ou un reçu
est hors de cette spec.
