# Spec — un `RAPPORT.md` déterministe, dérivé du reçu et de la trace

> V0.1 — 2026-10-21, née à **05:34:50** (`stat -c %w`), le nom porte `053343`, écart de **67 s**
> nommé. Suite du
> [brainstorm](../../../brainstorm/2026-10-21-053343-rapport-automatique.md), qui tranche la nature
> déterministe. **ADR-050** écrite après approbation.

## 1. Le manque

Le dossier d'un run porte `receipt.json` et `output.json`, mais le `RAPPORT.md` du second run du cas
jouet a été écrit **à la main** par un agent. Ce rapport dit ce que le verdict couvre, ce qu'il ne
couvre pas et quoi faire ensuite ; il dépend aujourd'hui de la présence d'un agent et de sa lecture.
La personne qui commande le test n'a aucun document automatique à ouvrir après `fin`.

Le rapport manuel du run `2026-10-20-222845-50664060-3d0db46` reste tel quel. Cette spec ne le réécrit
pas et ne prétend pas le reproduire mot pour mot.

## 2. La décision

Le rapport est une **vue déterministe** des pièces du run :

- aucune requête réseau, aucun modèle, aucune dépendance ;
- chaque phrase vient d'un champ du reçu, de l'output ou de la trace ;
- le rapport ne décide pas du verdict, ne relit pas les falsificateurs et ne réécrit aucune pièce ;
- deux exécutions sur les mêmes pièces rendent le même fichier, octet pour octet.

Le module s'appelle `docs/device/harness/rapport.mjs`. Il exporte
`ecrireRapport({ runDir, cas, remplacer })` et rend `{ chemin, ecrit, raison }`. Il n'importe rien
hors de `node:fs`, `node:path` et `node:crypto` si un hachage court est utile.

## 3. L'interface

`orchestrer.mjs` gagne une sixième commande :

```text
node docs/device/harness/orchestrer.mjs rapport --cas <id> --run <dir> [--remplacer]
```

- Elle exige un `receipt.json` lisible et un verdict parmi `conforme`, `ecart`, `non concluant` ;
  un reçu absent ou illisible est un refus nommé, `exit 1`, sans fichier écrit.
- Sans `--remplacer`, un `RAPPORT.md` déjà présent est refusé : le rapport d'un run n'est pas
  écrasé par accident. Avec `--remplacer`, il est réécrit ; le reçu et l'output ne bougent jamais.
- `fin` refuse avant le reçu si `RAPPORT.md` existe : un rapport déjà là ne doit pas rester à côté
  d'un reçu neuf. Après `output.json` et avant le bloc `▸ FIN`, il appelle la même fonction, qui écrit
  le rapport absent. Si cette écriture échoue, le reçu et l'output sont déjà écrits et la commande
  `rapport` permet de les relire pour écrire le document.
- `lire` ne change pas : elle reste sans écriture. Elle ne lit pas le rapport.
- `run.mjs` ne change pas : aucun nouveau champ du reçu, aucun nouveau falsificateur.

Le module lit les pièces par leurs chemins dans le dossier du run, pas par les chemins absolus que
le reçu cite : `receipt.json`, `output.json`, `trace/echange.jsonl`, `gate.json`, `faits.json`. Une
pièce absente est dite dans le rapport, jamais inventée.

## 4. Le rapport

Le fichier est `RAPPORT.md`, à la racine du run. Son en-tête est fixe :

```markdown
---
name: Rapport utilisateur — <cas>
description: <verdict> ; <une ligne de morsures et limites>
type: run-report
status: done
---

# Rapport utilisateur — <cas>

> Vue déterministe du reçu `<receipt.json>` et de la trace `<trace/echange.jsonl>`. Reçu écrit le
> `<recu_ecrit_le>`. Ce rapport ne remplace ni le reçu ni l'output.
```

Aucun horodatage de génération n'est écrit : le rapport ne dépend pas du moment où il est reconstruit.
Les dates citées sont celles du reçu ou de l'output.

Les sections, dans cet ordre :

### 1. La réponse

Trois phrases dérivées du verdict :

- `conforme` : « Le reçu conclut `conforme` : aucun falsificateur mesuré n'a mordu. » puis « Cela
  atteste la chaîne, la porte, la trace et l'ordre des gestes, pas la qualité du skill ni la justesse
  du produit. » ;
- `non concluant` : « Le reçu conclut `non concluant` : <morsures ou limites nommées>. » puis « Un
  non concluant n'est pas une défaillance du dispositif : il dit ce que la preuve ne permet pas de
  conclure. » ;
- `ecart` : « Le reçu conclut `ecart` : <morsures ou limites nommées>. » puis « L'écart est nommé ; il
  ne dit pas s'il vient du skill ou de la session. »

Si `output.json` existe, la phrase du juge est citée entre guillemets, sans être réécrite.

### 2. Ce qui a été testé

Un tableau à deux colonnes, une ligne par fait :

| Cas | `<cas>` |
| Session | `<outil>`, modèle `<modele>`, fil `<identifiant>`, ouverte par `<ouverte_par>` le `<ouverte_le>` |
| Budget | `<utilises>/<budget>` échanges, épuisé au `seq <n>` si `epuise_par` |
| Tableau | présent ou absent, `<lignes>` lignes, `<colonnes>` colonnes, `seq <n>` |
| Produit | `<n>` fichier(s), chemins relatifs sous `raw/<cas>/`, tailles |
| Révisions | framework `<framework_rev>`, terrain `<terrain_rev>` |
| Durée | de `<horodatage_debut>` à `<horodatage_fin>` |

Aucun chemin absolu de la machine n'est recopié : les liens vers le produit sont relatifs au run.

### 3. Ce que le reçu établit

Une liste dérivée des champs présents : le gel re-haché, la porte, la trace rejouée, la copie
re-hachée, le produit re-haché, le budget, le tableau. Une ligne dit ce qui est vérifié et le champ
qui le porte ; aucune ligne ne dit « tout est prouvé ».

### 4. Ce qu'il n'établit pas

Une liste fixe, plus les limites du reçu :

- la qualité du skill, la justesse du produit et la reproductibilité ;
- les gestes humains, qui reposent sur `temoignage` ;
- les lectures faites par un outil `shell`, dont la commande n'est pas dans la trace normalisée ;
- tout ce que `output.ecarte_comme_non_testable` nomme, recopié sans reformulation ;
- chaque entrée de `receipt.limites`, telle quelle.

### 5. Les morsures et les limites

Un tableau des falsificateurs qui mordent, avec une phrase par clé :

| Clé | Ce que la morsure dit |
| --- | --- |
| `birth_anterieur_au_gel` | un produit est né avant le gel |
| `arbre_de_travail_inchange` | le produit existe mais l'arbre de travail n'a pas bougé |
| `produit_identique_a_une_empreinte_anterieure` | le produit recopie un fichier déjà présent |
| `trace_sans_echange_dans_la_fenetre` | la trace ne porte aucun échange dans la fenêtre |
| `tableau_absent` | la trace ne porte aucun tableau rendu par la session |
| `ecriture_avant_tableau` | une écriture précède le tableau |
| `produit_ne_avant_le_tableau` | un produit est né avant le tableau |
| `lecture_hors_dossier` | une lecture est sortie du dossier du cas |

Une clé inconnue est nommée avec sa valeur JSON, jamais ignorée. Les limites sont ensuite listées,
une par ligne, avec leur texte d'origine.

### 6. Les lectures hors dossier

- Si `falsificateurs.lecture_hors_dossier` est un tableau non vide : un tableau `seq`, `outil`,
  `chemin`, puis la phrase « ces lectures interdisent `conforme` ».
- Si le champ existe et est vide : « le reçu ne nomme aucune lecture hors dossier ».
- Si le champ est absent : « ce reçu a été écrit avant l'ADR-049 ; il ne porte pas
  `lecture_hors_dossier`, donc le rapport ne peut pas conclure sur les lectures hors dossier ». Cette
  absence est aussi ajoutée aux limites.

La trace n'est pas re-jugée : le rapport ne recalcule pas les lectures hors dossier. Il lit le champ
du reçu, ou dit qu'il manque.

### 7. Les pistes

Une action par morsure ou limite, dans cet ordre de priorité :

| Condition | Piste |
| --- | --- |
| `attendu_incomplet` dans les limites | remplir le falsificateur de promesse, confirmer la promesse, re-geler |
| `tableau_absent` ou `ecriture_avant_tableau` | vérifier que la session rend un tableau avant d'écrire, puis rejouer |
| produit absent ou `arbre_de_travail_inchange` | vérifier le chemin produit et la collecte |
| `lecture_hors_dossier` non vide | rejouer dans un bac propre, sans accès aux autres cas |
| trace sans échange | vérifier l'export et le répertoire de session |
| `output.json` absent | écrire l'output du juge avant de conclure |
| `conforme` sans morsure | répéter sur un autre modèle ou un vrai dépôt, et lire le produit à la main |

Toute autre limite reçoit « relire la pièce nommée et corriger ce qu'elle dit », jamais une action
inventée. Si aucune piste ne s'applique : « aucune action dérivée ; relire le reçu et le produit ».

### 8. Où lire les preuves

Un tableau de liens relatifs : `receipt.json`, `output.json` s'il existe, `trace/echange.jsonl` s'il
existe, `gate.json`, `faits.json`, et chaque chemin de `produit.chemins`. Un lien dont la cible
manque est écrit en texte, avec « absent » ; le rapport ne crée pas de lien mort.

### 9. Ce que ce rapport ne prouve pas

Un paragraphe fixe : le rapport est une vue des pièces, pas un nouveau run ; il ne juge ni le contenu
ni la qualité ; il ne remplace pas la lecture humaine ; il ne mesure pas ce que le reçu ne mesure pas.

## 5. Les pièces absentes

Le rapport est écrit même si `output.json`, `trace/echange.jsonl`, `gate.json` ou `faits.json`
manquent : la section concernée dit « absent », et la limite correspondante est ajoutée. Seul un
`receipt.json` absent ou un verdict illisible fait refuser la commande. Un rapport qui ne peut pas
être dérivé ne s'écrit pas.

## 8. Ce que cette spec ne fait pas

- Aucune rédaction par un modèle, aucun appel réseau, aucune dépendance.
- Aucun nouveau falsificateur, aucun changement de `run.mjs`, du reçu ou de l'output.
- Aucun verdict caché : le rapport recopie le verdict du reçu.
- Aucune correction du rapport manuel du run historique.
- Aucun contrôle du contenu du produit : le rapport dit seulement ce que le reçu en mesure.
