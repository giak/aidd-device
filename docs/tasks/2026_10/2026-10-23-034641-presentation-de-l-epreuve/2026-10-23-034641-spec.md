# Spec — la présentation de l'épreuve

> 2026-10-23, Séance 126. Source : [le déroulé du test de `10-task`](../../../device/runs/2026-10-23-033645-guide-10-task/run-guide.md)
> §0, et le [gabarit du run guidé](../2026-10-22-221207-traces-et-run-guide/2026-10-22-221207-spec-run-guide.md).
> Corrige le protocole constaté : le gabarit ouvre sur « ce qui est testé » et laisse les enjeux, la méthode
> et les limites implicites.

## 1. Le défaut

Le §1 du gabarit décrit le skill et son produit. Il ne dit ni ce que la Task produite engage, ni comment
elle s'évalue, ni pourquoi le test vaut la peine, ni comment il sera conduit. Une personne qui valide ce
§1 valide une fiche, pas une épreuve.

## 2. La règle

Un run guidé s'ouvre par une **présentation de l'épreuve**, avant l'écriture de la demande. Elle porte six
champs, tous nommés :

1. **ce que tu vas tester** : le skill, et ce qui n'est pas testé ;
2. **pourquoi** : l'enjeu, la décision que le test éclaire, ce qu'un échec coûterait ;
3. **comment** : projet, demande, mode, trace, grille ;
4. **le but** : ce que le test veut établir ;
5. **ce qui sera observé** : gestes et pièces ;
6. **ce que le test ne prouvera pas**.

Un champ manquant vaut présentation non faite ; aucune demande n'est écrite.

## 3. Où elle vit

Dans le §0 du run-guide, le déroulé, avant le §1 de référence. Le §1 garde son rôle : décrire le skill,
son produit, ce que la Task engage et son évaluation. La présentation ne le remplace pas.

## 4. La validation

La personne valide la présentation, pas le §1 seul. Un refus rouvre la présentation ; il n'ouvre pas
l'étape suivante. Une fois validée, l'étape 3 écrit la demande (§2) et le produit attendu (§3).

## 5. Ce qui rendrait cette spec fausse

Une présentation qui n'énonce pas les enjeux. Une demande écrite avant la validation. Une présentation qui
répète le §1 sans dire pourquoi ni comment. Un run guidé conduit sans cette étape.

préparation sans cette présentation : `OPEN`, à aligner à la prochaine séance qui le touche.
