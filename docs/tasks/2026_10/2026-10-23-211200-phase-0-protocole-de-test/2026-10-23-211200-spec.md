## 2. Périmètre, et ce qui n'y entre pas

**Dans la phase 0 :**

- **C1** : `ouvrir` lance `opencode serve` avec un `HOME` et des `XDG_*` neufs, écrit
  `environnement.json` dans le run, et `suite` lit cette pièce pour exporter avec le même environnement ;
  `faits` et le reçu portent le bloc `environnement`, avec une limite quand il n'est pas isolé.
- **C2** : un cas `version_attendu: 2` déclare `unite_de_borne`, `borne_source` et `regles[]` ; chaque
  règle porte `mesure` ou `juge_seul`, et `borne_source` est une citation de la demande. `freeze` refuse
  une règle sans mesure, une unité hors domaine, une source absente ou un identifiant de falsificateur
  inconnu ; `receipt` refuse de même ; `fin --regle` cite la règle jugée.
- **C3** : la question se lit sur la dernière ligne hors bloc qui finit par `?`, pas seulement sur la
  dernière ligne du message.
- **C5** : `fin` exige `--attribution` et `--attribution-detail` pour `ecart` et `non concluant` ;
  le reçu, l'output et le rapport portent l'attribution ; `conforme` refuse une attribution.
- **Cinq contrôles** : 282, 283, 285, 286, 287.

**Hors phase 0 :** C4 (`--sans-ecrire`), C6 (modèle), C7 (vérification et mutations), C8 (contrat du
skill), C9 (famille et variantes), C10 (revue externe), C11 (correction de `06-test`), C12 (campagne L4).
Le vrai canari client, qui prouve que le binaire honoré ignore une configuration globale, est une
campagne séparée : le banc reste sec, sans session. Aucun cinquième verdict, aucun reçu réécrit, aucun
cas existant re-gelé, aucun run nouveau.

**Compatibilité.** Les cas sans `version_attendu` (tous les cas gelés aujourd'hui) gardent le
comportement actuel : ni `regles`, ni `unite_de_borne` ne leur sont demandés. Un `faits.json` sans bloc
`environnement` reste lisible et reçoit une limite. Un reçu antérieur n'est jamais réécrit.

## 3. C1 — l'environnement isolé, et sa déclaration

### 3.1 Les chemins

`ouvrir` dérive la racine du cas de l'arbre `travail` du gel, sans nouveau champ :

```text
caseRoot = dirname(travail)                      // <racine>/<cas>
envDir   = <caseRoot>/environnement/<run>        // <run> = basename du dossier du run
home     = <envDir>/home
config   = <envDir>/config
data     = <envDir>/data
cache    = <envDir>/cache
state    = <envDir>/state
```

Le dossier `envDir` et ses cinq sous-dossiers sont créés par `ouvrir`, avec `mkdirSync(..., {recursive:
true})`. Aucun n'est dans le dépôt : `caseRoot` est hors des quatre arbres.

### 3.2 Les variables

Pour le serveur **et** pour l'export, `ouvrir` et `suite` passent le même environnement :

```text
HOME              = <home>
XDG_CONFIG_HOME   = <config>
XDG_DATA_HOME     = <data>
XDG_CACHE_HOME    = <cache>
XDG_STATE_HOME    = <state>
```

`OPENCODE_CONFIG`, `OPENCODE_CONFIG_DIR`, `OPENCODE_CONFIG_CONTENT` et `OPENCODE_HOME` sont retirés de
l'environnement transmis, jamais laissés à l'héritage. `spawn` reçoit `env` ; `execFileSync` reçoit
`env`. Le `PATH` reste celui de l'opérateur, sinon le binaire ne se trouve plus.

`--api` est une exception déclarée : aucun serveur n'est lancé, aucun `HOME` neuf n'est créé, et le
sidecar porte `isole: false, mode: "api", raison: "api_externe"`. Le reçu en tire la limite.

### 3.3 Le sidecar `environnement.json`

`ouvrir` écrit **une seule** pièce dans le run, après le démarrage du serveur et avant la création de
la session :

```json
{
  "type": "environnement",
  "isole": true,
  "mode": "serve",
  "home": "<absolu>",
  "xdg_config": "<absolu>",
  "xdg_data": "<absolu>",
  "xdg_cache": "<absolu>",
  "xdg_state": "<absolu>",
  "binaire": "<absolu ou null>",
  "cree_le": "<ISO 8601 local>"
}
```

Pour `--api` : `isole: false`, `mode: "api"`, `raison: "api_externe"`, et les cinq chemins à `null`.
Un second `ouvrir` sur le même run est refusé si `environnement.json` existe : un run, un environnement.
Le run se rejoue avec un nouveau dossier, comme la porte.

Le bloc `▸ FIN` d'`ouvrir` remplace « aucune : ouvrir n'écrit rien » par le chemin du sidecar. Le
protocole §2 est amendé : `ouvrir` n'écrit qu'une pièce de déclaration, jamais une mesure.

### 3.4 `suite`, `faits`, reçu

`suite` lit `<run>/environnement.json` :

- présent et `isole: true` : `faits.environnement` recopie les cinq chemins et le mode, et
  `exportTrace` reçoit `env` avec les mêmes variables ; sans `--store`, le store est le premier chemin
  qui existe, `<data>/opencode` puis `<home>/.local/share/opencode`, et `faits.trace.store` le porte ;
  aucun des deux ne rend `suite` silencieux : il refuse, le client n'a pas écrit de store dans
  l'environnement isolé ;
- présent et `isole: false` : `faits.environnement` recopie la raison, et la limite
  `environnement_non_isole` est ajoutée plus tard par le reçu ;
- absent : `faits.environnement = {isole: false, raison: "absent"}` ; le reçu ajoute
  `environnement_non_mesure` et reste lisible (cas antérieurs) ;
- un chemin nommé par le sidecar n'existe pas : `isole: false`, `raison: "chemin_absent"`, le chemin
  cité, et la limite correspondante. `suite` ne refuse pas : le run existe, l'isolement est seulement
  non tenu ;
- `--store` donné : il gagne, et si le store diffère de `<data>/opencode`, la limite
  `store_hors_environnement` le dit.

Le reçu copie `faits.environnement` sous `environnement` et ajoute, quand `isole` est vrai :

```text
l'environnement est déclaré par le lanceur (HOME et XDG_* neufs), le reçu ne prouve pas que le client
l'a respecté ; le canari client est une campagne séparée
```

Le `blocVerdict` dit `environnement : isolé | non isolé (<raison>)`. Le rapport §5 le reprend.

## 4. C2 — une règle, une mesure

### 4.1 Le schéma d'un cas v2

`cas` écrit `version_attendu: 2` dans le squelette, et le produit gagne trois champs :

```json
"produit": {
  "racine": "terrain/test_skill_analysis.py",
  "regle": "au plus deux tests, un par comportement",
  "arbre_attendu": ["test_skill_analysis.py"],
  "unite_de_borne": "test_fonction",
  "borne_source": "au plus deux tests, un par comportement approuvé",
  "regles": [
    { "id": "R1", "texte": "un seul fichier neuf à la racine du terrain", "mesure": "F3" },
    { "id": "R2", "texte": "le contenu du test est juste", "juge_seul": true, "raison": "le contenu ne se mesure pas par une commande" }
  ]
}
```

- `unite_de_borne` ∈ `test_fonction | cas_de_test | comportement` ;
- `borne_source` est une citation exacte de la demande (espaces normalisés), pas une reformulation ;
- `regles[]` a au moins une entrée ; chaque `id` est unique et commence par `R` ;
- chaque règle porte **exactement** `mesure` (un `id` de `falsificateurs_du_run`) ou `juge_seul: true`
  avec une `raison` non vide ; les deux ensemble, ou aucun des deux, sont refusés ;
- le squelette de `cas` porte `unite_de_borne: null`, `borne_source: null`, `regles: []`, et le
  falsificateur `P` garde `a_remplir: true`. Tant que `a_remplir` est vrai, le gel est accepté et le
  reçu plafonne à `non concluant` (ADR-039) ; une fois `P` rempli, les trois champs sont exigés.

### 4.2 Ce que `freeze` refuse

`freeze` lit l'attendu. Si `version_attendu >= 2` et que l'attendu n'est plus `a_remplir`, il refuse :

```text
freeze : la règle R1 n'a ni mesure ni juge_seul — une règle sans falsificateur sort du reçu (ADR-085)
freeze : la règle R1 mesure « F42 », absent des falsificateurs — une mesure qui ne nomme rien ne mesure rien
freeze : unite_de_borne vaut « … », attendu test_fonction | cas_de_test | comportement
freeze : borne_source « … » n'est pas dans la demande — la borne se cite, elle ne s'invente pas
freeze : regles est vide — un cas v2 sans règle mesurable n'a pas d'instrument
```

La validation lit le fichier `*.request.md` du même cas pour `borne_source` ; la comparaison normalise
les espaces, pas la ponctuation. Un cas v1 (sans `version_attendu`) n'est jamais validé ainsi.

### 4.3 `receipt` et `fin`

`receipt` refait les mêmes contrôles sur l'attendu gelé (défense en profondeur) et écrit :

```json
"regles": { "total": 2, "mesurees": 1, "juge_seul": 1, "sans_mesure": [] },
"regle_jugee": "R1"
```

`--regle <id>` est une option de `receipt` et de `fin`. Pour un cas v2 et `--verdict ecart`, elle est
obligatoire : `fin` refuse sans elle, et `receipt` refuse un `id` absent de `regles[]`. Pour
`non concluant`, elle est facultative (la cause peut être le cas lui-même). `compare` recopie
`regle_jugee` dans `output.json`, et le rapport imprime « règle jugée : R1 ».

Aucun verdict n'est dérivé automatiquement des règles : le juge décide, et la règle rend sa décision
citable. Une règle `juge_seul` est une limite, jamais un refus.

## 5. C3 — la question, pas la dernière ligne

`derniereLigneHorsBloc` reste pour le refus. Une seconde fonction, `derniereQuestionHorsBloc`, parcourt
les mêmes lignes hors blocs clôturés et rend **la dernière ligne non vide qui finit par `?`**, même si
des lignes non interrogatives la suivent. `derniereReponseEnTexte` rend `{ ligne, question, id }` :

- `ligne` est la dernière ligne, celle que le refus cite ;
- `question` est la dernière ligne interrogative, celle que `ouvrir` joue ;
- `id` est l'identifiant du message, pour ne pas le rejouer.

`commandeOuvrir` remplace `texte.ligne.endsWith("?")` par `texte.question !== ""`. Le refus
`la session … s'est arrêtée sans question` garde `texte.ligne`. Le bloc des réponses cite
`question` au lieu de `ligne`. Le chemin formulaire, l'ordre des réponses figées et le comptage ne
bougent pas.

Limite assumée : une ligne qui finit par `?` sans être une question (rhétorique, URL) est prise pour
une question. La règle reste mécanique et bornée ; le cas fige les réponses, et une question de trop est
un refus qui nomme le compte.

## 6. C5 — le verdict nomme sa couche

### 6.1 Les options

`fin` et `receipt` gagnent :

```text
--attribution <skill|cas|harnais|environnement|session|inconnu>
--attribution-detail <texte>
```

`--regle <id>` vient de C2. Pour `ecart` et `non concluant`, `--attribution` et un détail non vide sont
obligatoires. Pour `conforme`, une attribution est refusée : un run conforme n'a pas de couche fautive.
`inconnu` est admis, mais il exige un détail et ajoute la limite `cause_non_etablie` ; il ne remplace
jamais une couche que la preuve nomme.

Refus, tous en `1` et nommant l'option :

```text
fin : --verdict ecart exige --attribution (skill|cas|harnais|environnement|session|inconnu) — un écart sans couche ne dit pas qui a fauté
fin : --attribution-detail est vide — la couche se nomme, la pièce se cite
fin : --verdict ecart exige --regle <id> pour un cas v2 — la règle violée se cite
receipt : attribution « conforme » refusée — un run conforme n'a pas de couche fautive
```

### 6.2 Les pièces

Le reçu porte :

```json
"attribution": { "couche": "session", "detail": "le produit porte quatre fonctions pour deux comportements" },
"regle_jugee": "R1"
```

`output.json` recopie les deux champs depuis le reçu, sans les réinterpréter. Le rapport imprime une
section « L'attribution » avec la couche, le détail et la règle. La page `RESULTAT.md`, quand le cas en
déclare une, ajoute une phrase en clair : `skill` => « la consigne du skill », `cas` => « le cas »,
`harnais` => « le harnais », `environnement` => « l'environnement du client », `session` => « la
session », `inconnu` => « une cause non établie ». Le vocabulaire technique reste dans le rapport.

Le reçu ajoute la limite, sur le modèle de la conduite :

```text
l'attribution est déclarée par le juge : le reçu ne prouve pas la couche, il la nomme (ADR-086)
```

## 10. ADR réservées

- **ADR-084** : `ouvrir` isole l'environnement du client et écrit `environnement.json` ; c'est la
  première pièce que `ouvrir` écrit, et elle déclare, elle ne mesure pas.
- **ADR-085** : une règle de produit sans falsificateur est `juge_seul` ou refusée ; `unite_de_borne`
  et `borne_source` rendent la borne citable.
- **ADR-086** : un verdict `ecart` ou `non concluant` nomme sa couche ; `conforme` n'en a pas.

## 11. Ce que cette spec ne fait pas

- Elle ne corrige pas `fin --sans-ecrire` (C4) : le contrôle 284 reste libre.
- Elle ne déclare ni n'impose le modèle du skill (C6) : le run peut encore tourner sur un autre modèle.
- Elle n'injecte aucune faute dans le produit (C7) : `9 passed` reste une exécution, pas une preuve.
- Elle n'ajoute pas le contrat du skill (C8), la famille de cas (C9), la revue externe (C10), la
  correction de `06-test` (C11) ni la campagne L4 (C12).
- Elle ne prouve pas que le vrai client respecte l'environnement : le canari est une campagne.
- Elle ne juge pas le contenu du produit, et ne rouvre aucun reçu.
- Elle ne touche ni au gel, ni à la porte, ni au budget, ni aux quatre blocs.

## 12. Ce qui la rendrait fausse

- Un `ouvrir` qui dit `isole: true` sans sidecar, ou un `suite` qui exporte depuis le store de
  l'opérateur en portant `isole: true`.
- Un cas v2 dont une règle sans mesure passe le gel, ou dont un `borne_source` absent de la demande
  passe.
- Un `fin --verdict ecart` sans attribution, ou un `conforme` avec attribution, accepté.
- Une question qui ne se lit encore que sur la dernière ligne, ou un `?` dans un bloc pris pour une
  question.
- Un contrôle 282 qui passe sans faux `opencode` dans le `PATH`, ou un contrôle 283 qui passe sur un
  message dont la question est la dernière ligne.
- Un reçu antérieur modifié, ou un cas v1 refusé faute de `version_attendu`.
