# Spec — deux clients pour le même test, opencode et Freebuff

> 2026-10-20, nom `181451`, né à 18:15:44 (`stat -c %w`), écart de 53 s nommé. Source :
> [le brainstorm du 2026-10-20](../../../brainstorm/2026-10-20-180518-deux-clients-opencode-et-freebuff.md).
> Le brainstorm a été approuvé par « écris la spec ». Cette spec ne code rien : elle attend
> l'approbation qui précède l'implémentation. Les ADR **043 à 046** sont réservées.

## 1. But

Le même cas, le même gel, la même porte, le même texte et le même reçu, conduits sous **opencode** ou
sous **Freebuff**. Le client est un fait du run, jamais un paramètre du cas. Le harnais lit les deux
clients par une frontière unique, et le reçu re-dérive du client les faits du client.

Ce que la spec change : `faits`, `receipt`, `orchestrer.mjs suite`, le banc et les pages. Ce qu'elle
ne change pas : le gel, la porte, le texte, les réponses figées, le budget, les falsificateurs F1 à
F9, la destination du produit, les conditions du verdict, la règle « un run, un dossier ».

## 2. Décisions

- **ADR-043, frontière d'adaptation.** Un module `docs/device/harness/clients.mjs` expose deux
  implémentations derrière une interface normalisée. `faits` et `receipt` ne lisent plus un schéma de
  client directement ; ils lisent le modèle normalisé.
- **ADR-044, le client est un fait du run.** Le cas ne nomme aucun client. `faits.session.outil` et
  `faits.trace.client` le disent, et le reçu le vérifie. Le même cas doit pouvoir tourner sous l'un
  ou l'autre.
- **ADR-045, l'ordre de la trace est celui des lignes.** Le `seq` reste le numéro de message ; deux
  parts d'un même message le partagent. `tableauDeTrace` rend un `index` (position dans le JSONL), et
  `ecrituresAvant` compare les `index`. Une écriture qui précède le tableau dans le même message est
  donc vue, pour les deux clients.
- **ADR-046, l'export opencode est normalisé.** Le CLI rend un JSON ; l'adaptateur le normalise en
  JSONL. Le JSONL normalisé est la condition du reçu ; l'export brut est conservé et haché, mais il
  n'est pas comparé octet à octet, parce que `info.time.updated` et les jetons changent si la session
  bouge.

## 3. La frontière

`clients.mjs` exporte :

```text
detect(fil, { gel, store, cwd }) -> { client, session } | null
session(client, fil, { base, store, cwd }) -> session normalisée
premierMessage(client, fil, opts) -> { ts, seq }
budget(client, fil, n, opts) -> { utilises, epuise_seq, epuise_ts }
exportTrace(client, fil, { dest, brut, base, store, cwd }) -> { commande, source, cwd, sha256, brut_sha256 }
replayTrace(client, fil, opts) -> { octets, sha256, brut_octets, brut_sha256 }
commandeAttendue(client, fil, { base, store, cwd }) -> string
```

### 3.1 La session normalisée

```json
{
  "outil": "freebuff",
  "application": "Freebuff Desktop (desktop-v2.db, harness_id ...)",
  "identifiant": "...",
  "modele": "...",
  "ouverte_le": "2026-10-18T07:56:25+02:00",
  "repertoire_de_travail": "/abs/vers/terrain",
  "execution_mode": "local",
  "worktree": null,
  "premier_message": { "ts": "2026-10-18T07:56:30+02:00", "seq": 1 }
}
```

Pour opencode : `outil = "opencode"`, `application = "opencode <version> (<chemin du binaire>, agent
<agent>)"`, `modele = <providerID>/<id>`, `ouverte_le = info.time.created`, `repertoire_de_travail =
info.location.directory`, `execution_mode = "local"` si le répertoire résout et est un répertoire,
`worktree = null`, `premier_message = { ts: premier messages[].type == "user".time.created, seq: son
rang }`.

Pour Freebuff : les valeurs actuelles de `threads` (`project_path`, `model`, `created_at`,
`execution_mode`, `branch`, `worktree_path`, `harness_id`) et du premier `messages.role = 'user'`.
`worktree` vaut `{ branche, chemin }` si l'un des deux champs est non vide, `null` sinon.

Le répertoire est comparé, après résolution des liens, au `travail` du gel. Une session ouverte
ailleurs est refusée ; le texte nomme le répertoire de la session et celui du gel.

### 3.2 La trace normalisée

Une ligne JSONL par part :

```json
{ "seq": 12, "role": "assistant", "kind": "tool", "open": null,
  "outil": "read", "chemin_outil": "/abs/...", "text": null, "ts": 1792511390017 }
```

- Freebuff : la requête SQL actuelle, champ pour champ.
- opencode : `user` -> `kind = "text"`, `text = message.text` ; `assistant.content[]` : `text` ->
  `kind = "text"`, `reasoning` -> `kind = "reasoning"`, `tool` -> `kind = "tool"`, `outil = part.name`,
  `chemin_outil = state.input.path ?? state.input.filePath ?? state.input.file_path ?? null` ;
  `synthetic` -> `kind = "text"`, `text` conservé ; `idle` sans texte ignoré. `open` vaut `null`.
- L'ordre des lignes est l'ordre des messages puis des parts. C'est lui que le reçu lit ; `seq` ne
  sert qu'à nommer le message.

## 4. Interfaces

### 4.1 `faits`

```text
node docs/device/harness/run.mjs faits --case <id> --client <freebuff|opencode> \
  [--base <desktop-v2.db>] [--store <racine opencode>] --fil <id> \
  --trace <fichier> --out <faits.json> --par <qui> --fin <date -Is> --temoignage <texte>
```

- `--client` est optionnel. Sans lui, `--base` implique `freebuff` et `--store` implique `opencode` ;
  les deux ensemble sont un refus, aucun des deux est un usage (`exit 2`). Avec `--client`, `--base`
  est obligatoire pour Freebuff et refusé pour opencode ; `--store` est refusé pour Freebuff et vaut
  `~/.local/share/opencode` par défaut pour opencode. Ce défaut garde les 153 contrôles existants,
  qui passent `--base` sans `--client`.
- `--fil` : lettres, chiffres, tirets et soulignés seulement (règle actuelle).
- `--trace` : le JSONL normalisé, écrit par l'adaptateur.
- `--out` : `faits.json`, écrit une fois, jamais réécrit.

`faits.json` gagne :

```json
"session": { "outil": "opencode", "...": "les champs actuels" },
"trace": {
  "client": "opencode",
  "source": "opencode <version> (CLI export, store <store>)",
  "store": "<store>",
  "cwd": "/abs/vers/terrain",
  "chemin_exporte": "<run>/trace/echange.jsonl",
  "export_brut": "<run>/trace/export-brut.json",
  "commande": "opencode session export <id>"
}
```

Pour Freebuff, `trace.base` reste le `desktop-v2.db` ; `trace.store`, `trace.export_brut` et
`trace.cwd` sont absents.

### 4.2 `receipt`

Aucune option nouvelle. Il lit `faits.session.outil` et `faits.trace.client`, refuse s'ils diffèrent
ou s'ils ne valent pas `freebuff|opencode`, puis :

- **Freebuff** : le comportement actuel, inchangé. `trace.base` doit être un fichier ; la requête SQL
  est rejouée ; `from messages` et `thread_id='…'` restent exigés ; le budget vient de la base.
- **opencode** : l'export est rejoué par l'adaptateur, dans `trace.cwd` ; le reçu compare `info.id`,
  `info.location.directory` au `travail` du gel, `info.model` à `session.modele`,
  `info.time.created` à `session.ouverte_le`, le premier `user` à `horodatage_debut`, le compte des
  `user` à `echanges`. Il normalise l'export rejoué et compare son sha256 à `trace.chemin_exporte`.
  `trace.commande` doit être `commandeAttendue("opencode", ...)` ; le reçu ne l'exécute jamais comme
  une chaîne. Le brut rejoué est haché ; s'il diffère du brut conservé, le reçu porte la limite
  `export_brut_instable`, jamais un refus : le JSONL normalisé est la condition.
- `trace.cwd` doit résoudre au `travail` du gel, pour opencode.
- `trace.store` doit exister et être un répertoire, pour opencode.

Le reçu gagne `session_verifiee.outil` pour les deux clients. Pour Freebuff, `session_verifiee` garde
ses champs actuels et `trace_verifiee` reste `{ sha256, rejoue_le }`. Pour opencode :
`session_verifiee = { outil, store, fil, repertoire_de_travail, modele, ouverte_le, premier_message }`
et `trace_verifiee = { outil, commande, cwd, sha256, brut_sha256, rejoue_le }`. Le `tableau` gagne
`index` ; les entrées de `ecriture_avant_tableau` gagnent `index`. Le `seq` reste.

### 4.3 `orchestrer.mjs suite`

```text
node docs/device/harness/orchestrer.mjs suite --cas <id> --fil <id> \
  [--run <dir>] [--client <auto|freebuff|opencode>] [--store <racine opencode>] \
  [--produit <chemin> | --sans-produit]
```

- `--client` vaut `auto` par défaut.
- `auto` essaie Freebuff (les bases `~/.config/freebuff-desktop/projects/*/desktop-v2.db`), puis
  opencode (`opencode session export <fil>` dans le `travail` du gel). Les deux -> refus et
  `--client` ; aucun -> refus qui nomme les deux sources.
- `--client` explicite ne consulte que ce client ; un échec est un refus qui nomme la raison.
- `suite` crée `trace/` et un `echange.jsonl` vide avant `faits`, comme aujourd'hui ; `exportTrace`
  l'écrase. Après `faits`, `suite` appelle `exportTrace` de l'adaptateur et n'exécute plus `bash -c` sur
  `faits.trace.commande`. Le bloc d'étape imprime la commande rendue par l'adaptateur.
- `--store` vaut `~/.local/share/opencode` par défaut ; il est enregistré et remis à `faits`. Avec
  `--client freebuff`, `--store` est refusé ; avec `auto`, il ne sert qu'à la détection opencode.

## 6. Banc

### 6.1 Fixtures opencode

Un faux binaire `opencode` dans `PATH`, qui répond à `--version` (`opencode v2.0.32`) et à
`session export <id>` en recopiant une fixture JSON ; aucun réseau. Le banc pose aussi
`HOME=$B/home`, avec une base Freebuff de fixture sous `.config/freebuff-desktop/projects/`, pour que
`suite` auto trouve (ou non) les deux clients. Les fixtures sont fabriquées, petites, et ne reprennent
pas la session réelle :

- `banc-opencode-ok` : `location = $W/terrain`, 1 `user`, un tableau dans une part `assistant/text`,
  une lecture, une écriture, une instruction `synthetic` qui contient un tableau, un `reasoning` qui
  contient un tableau.
- `banc-opencode-ailleurs` : `location = $W/ailleurs`.
- `banc-opencode-sans-location` : `info.location` absent.
- `banc-opencode-sans-modele` : `info.model` absent.
- `banc-opencode-sans-user` : aucun message `user`.
- `banc-opencode-budget-4` : 4 messages `user`, budget 3.
- `banc-opencode-ordre` : une écriture dans le même message assistant que le tableau, avant lui,
  puis une écriture après lui.
- `banc-opencode-modele` : modèle différent de `faits.json`.
- `banc-opencode-premier` : premier `user` différent de `horodatage_debut`.
- Un identifiant `banc-ambigu` inséré aussi dans la base Freebuff, pour l'ambiguïté.

### 6.3 Ce que le banc ne prouve pas

Le faux `opencode` n'est pas le CLI réel : il prouve l'adaptateur, pas le client. La fixture
`banc-opencode-ordre` prouve l'ordre des lignes, pas la génération réelle d'une écriture et d'un
tableau dans le même message. Le brut rejoué instable est une limite, pas un refus.

Dix refus du §5 n'ont pas de contrôle dédié dans les dix-huit : 1, 4, 5, 9, 11, 12, 13, 16, 17 et
18. Ils sont dans le code et dans les pages, mais le banc ne les éprouve pas ; les ajouter est un
travail nommé, pas un acquis.

## 8. Critères d'acceptation

1. `faits --client opencode` sur `banc-opencode-ok` écrit les champs de session et de trace listés au
   §4.1, et `receipt` rend un reçu avec `session_verifiee.outil = "opencode"`.
2. Modifier `trace/echange.jsonl` après l'export fait refuser `receipt` en `exit 1` ; modifier
   l'export brut fait seulement apparaître la limite `export_brut_instable`.
3. Une session ouverte dans `<W>` est refusée par `faits` et par `suite`, avec les deux chemins.
4. Une écriture avant le tableau dans le même message donne `ecriture_avant_tableau` non vide et
   refuse `conforme` ; une écriture après ne la donne pas et laisse `conforme` passer, les autres
   falsificateurs muets.
5. L'ambiguïté des deux clients refuse `suite` sans `--client` et passe avec `--client opencode`.
6. Les 153 contrôles Freebuff passent ; le `tableau` gagne `index`, une addition ; un contrôle qui
   comparerait l'objet entier est mis à jour avec le champ, jamais affaibli. Les 18 nouveaux passent ;
   le banc rend **171/171**, `exit 0`.
7. `node docs/device/harness/liens.mjs` rend 0 lien mort, `exit 0` ; le contrôle 153 confronte
   toujours le runbook et l'annexe au code. Le runbook porte les nouvelles options ; l'annexe garde sa
   forme minimale et n'invente rien.
8. Les pages du §7 sont à jour ; aucune ne nomme une option ou un refus qui n'existe pas.
9. Le run opencode réel, ouvert dans `<W>/terrain`, écrit le premier `receipt.json` avec
   `session.outil = "opencode"` ; la session `<W>` reste refusée. Ce critère dépend des trois gestes
   humains et se ferme à la séance, pas au banc. **Fermé le 2026-10-20** par le run
   `docs/device/runs/2026-10-20-202333-50664060-1028c8b` : reçu `non concluant`, session
   `ses_ea564a976ffevcpzB4aY03ELBF`, session `<W>` refusée par `faits` et `suite`. Limite nommée : les
   trois gestes ont été exécutés par l'agent via l'API du client, pas par une personne devant
   l'interface.

## 10. Ce que cette spec ne promet pas

- L'intégrité du client ni du CLI : un faux `opencode` peut forger un export, comme un faux `sqlite3`
  peut forger une base. Le banc le fait exprès ; le dispositif ne signe pas le client.
- L'absence de bug dans la normalisation : le reçu rejoue avec le même adaptateur, donc un bug
  systématique est invisible ; les fixtures adversariales (tableau `synthetic`, tableau `reasoning`,
  écriture avant/après) le réduisent, ne l'éliminent pas.
- La stabilité du format opencode : une version qui change la forme de l'export est refusée ou
  limitée, jamais devinée.
- Le modèle, la qualité du skill, la justesse du produit.
- L'instant du tableau : `tableau.ts` est le début du message assistant, pas la part ; F1 garde cette
  limite, avec la résolution d'une seconde du `birth`.
- Le champ de chemin d'une écriture opencode non mesurée : la fixture couvre `write`/`edit` avec
  `path` et `filePath` ; un outil réel qui nommerait autrement reste une limite nommée.
- Le compte des commandes du harnais : la dérive « six » contre sept (`texte`) reste hors de cette
  spec.
- La session `<W>` : elle est hors cadre, ne produit aucun reçu, et le restera.
