## 1. La question

La Task produite par le run guidé décrit un contrôle de démarrage. Est-elle actionable, et son effet est-il
celui qu'elle promet ? Une Task est un document : elle ne fait rien par elle-même. L'épreuve consiste donc à
implémenter ce contrôle dans une copie, puis à exécuter les quatre cas de configuration que son `Done When`
nomme, sur cette copie et sur une copie témoin sans le contrôle.

## 2. Le contrôle

`config_startup_error(path)` lit `data/config.json` et rend `None` si le démarrage est permis, sinon la raison
du refus. Elle est appelée une seule fois, dans `if __name__ == '__main__'` : un refus écrit
`Démarrage refusé : …` sur `stderr` et sort avec le code `1`. Le contrôle n'est pas posé à l'import :
la fixture de `test_app.py` remplace `app.CONFIG_PATH` après l'import (ligne 27 de la copie), et un contrôle à l'import
lirait le `data/` réel au lieu du dossier temporaire des tests.

Le contrôle n'utilise pas `load_json()`, qui retourne un défaut sur JSON corrompu et journalise : c'est
précisément le silence que la Task veut empêcher. Absence du fichier = premier lancement normal, donc
démarrage accepté ; fichier présent mais inutilisable = refus.

Diff : `app.py` +31 lignes, `test_app.py` +39, **70 insertions, 0 suppression**.

## 3. Les quatre cas

Script `cas-quatre.sh` à côté de la copie, lancé par `bash cas-quatre.sh <terrain>`. Chaque cas lance la
commande réelle `python3 app.py`, sonde `http://127.0.0.1:8765/config` pendant 10 s et enregistre le code de
sortie et la première ligne de `stderr`.

| Cas | `data/config.json` | Attendu | Copie avec contrôle | Copie témoin |
|---|---|---|---|---|
| 1 absent | aucun fichier | démarre | HTTP 200 | HTTP 200 |
| 2 JSON illisible | `{"active": 0, "configs": [` | refuse | `exit 1`, message | HTTP 200, **écart** |
| 3 profil hors bornes | `{"active": 3, "configs": [{"name": "a"}]}` | refuse | `exit 1`, message | HTTP 200, **écart** |
| 4 profil valide | `{"active": 0, "configs": [{"name": "a", "source_data": "", "epars_dirs": []}]}` | démarre | HTTP 200 | HTTP 200 |

Messages rendus, cités au plus court :

- cas 2 : `Démarrage refusé : …/data/config.json est illisible (JSONDecodeError)` ;
- cas 3 : `Démarrage refusé : …/data/config.json désigne un profil actif hors bornes (active=3, 1 profils)`.

La copie témoin est la même copie, `app.py` et `test_app.py` rendus à `HEAD` par `git checkout --`. Sans le
contrôle, les cas 2 et 3 démarrent et répondent HTTP 200 : l'effet mesuré vient bien de la Task, pas du
terrain ni du protocole de lancement.

## 4. Les tests

Quatre tests neufs dans `test_app.py`, un par cas, plus la forme « clés manquantes » du profil valide :

- `test_config_startup_absent_accepts_start`
- `test_config_startup_unreadable_json_refuses`
- `test_config_startup_no_valid_profile_refuses` (deux formes : `active` hors bornes, `configs` absent)
- `test_config_startup_valid_profile_accepts_start`

`python3 -m pytest -q test_app.py -k config_startup` => **4 passed**, `exit 0`.
`python3 -m pytest -q test_app.py` => **200 passed, 1 failed**. L'échec est
`test_cache_buster_covers_css`, qui exige `static/dist/script.css`, absent tant que `npm run build` n'a pas
tourné ; une copie témoin rend le même échec seul (**196 passed, 1 failed**). Les quatre tests neufs
expliquent l'écart de compte entre les deux copies.

## 5. Ce que l'épreuve établit

- La Task est actionable : 25 lignes de contrôle et un appel au démarrage suffisent à satisfaire ses quatre
  conditions, sans toucher au reste de `app.py`.
- Son effet est celui qu'elle annonce, sur les quatre cas, mesuré par la commande réelle et non par la
  fonction seule.
- Le profil à clés manquantes, que `test_get_active_config_missing_keys` verrouille, reste accepté : le
  contrôle ne casse pas le comportement que la Task ne voulait pas changer.

## 6. Ce que l'épreuve n'établit pas

- **Qu'une session produirait ce contrôle.** L'épreuve juge la Task, pas le geste qui l'a écrite ; elle ne
  dit rien de l'indépendance du run guidé, toujours non mesurée.
- **Que « message explicite » et « code non nul » soient pinnés.** La Task ne fixe ni le texte ni la valeur :
  j'ai choisi une ligne sur `stderr` et le code `1`. Un autre choix satisferait la Task aussi.
- **Que les formes hors des quatre cas soient refusées.** Un profil actif qui n'est pas un objet JSON passe,
  et `active` booléen passe pour l'entier `1` en Python ; aucun des quatre cas ne les couvre, et la Task ne
  les nomme pas.
- **Que le contrôle couvre la vie du processus.** Il lit le fichier au démarrage seulement ; un
  `POST /config` qui écrit une configuration invalide n'est pas refusé, ce que la Task ne demande pas.
- **L'absence littérale.** La demande d'origine parlait d'échouer « quand le fichier manque » ; la Task
  tranche l'inverse pour l'absence, comme le run du 21:37 l'avait décidé. L'épreuve suit la Task, pas la
  demande d'origine.
