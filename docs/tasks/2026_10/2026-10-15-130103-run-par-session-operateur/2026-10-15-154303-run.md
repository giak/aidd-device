Sa formule se recalcule **sans réécrire un chemin** : les deux fichiers du cas se lisent depuis la
racine du dépôt, les huit références depuis un checkout de l'arbre que le gel nomme. Ce checkout est
le seul paramètre qu'un tiers fournit, avec la révision gelée : les `remotes` de l'arbre disent où
le prendre.

```text

python3 - <<'PY'

RACINE=os.getcwd(); CAS="2026-10-15-133423-promesse-memoire-avant-ecriture"; FR=os.environ.get("RACINE_FRAMEWORK","")

    ok.append(h==x["sha256"]); print("fichier", x["role"], h==x["sha256"])
for label in sorted({r["arbre"] for r in g["references"]}):

    ok.append(h==r["sha256"]); print("reference", r["chemin"], h==r["sha256"])

→ **complet** (`head_complet`) : `--short` s'abrège par dépôt, le même commit rend 7 caractères
```

### 1.5 Où vit la trace machine, et comment on l'exporte

**Le client du second run est Freebuff** (décision du 2026-10-15, après le premier run, qui
utilisait `opencode`) : sa trace machine vit dans une base SQLite par projet,
`~/.config/freebuff-desktop/projects/<projet>-<uuid>/desktop-v2.db`, tables `threads` et `messages`.
Les trois sources constatées sur cette machine (spec §5.1) restent : Freebuff Desktop
(`desktop-v2.db`, chaque geste est une part de `parts_json`), `claude` CLI
(`~/.claude/projects/<cwd-encodé>/<session>.jsonl`), `opencode`
(`~/.local/share/opencode/opencode.db` et `storage/{session,message}`). Le harnais n'en lit
**aucune** : il ne fait que constater que `chemin_exporte` existe.

L'export de la session Freebuff : une ligne JSON par part, dans l'ordre des messages.

```text
sqlite3 -readonly ~/.config/freebuff-desktop/projects/<projet>-<uuid>/desktop-v2.db "
  select json_object('seq', m.seq, 'role', m.role, 'kind', json_extract(value,'$.kind'),
                     'open', json_extract(value,'$.open'), 'text', json_extract(value,'$.text'),
                     'ts', m.ts)
    from messages m, json_each(m.parts_json)
   where m.thread_id='<thread>' order by m.seq, json_each.key;" > "$RUN/trace/echange.jsonl"
```

Éprouvé le 2026-10-15 sur ce poste : 533 lignes pour une session d'audit, une par part, les genres
rencontrés étant `text`, `reasoning`, `tool`, `changes`, `compaction` et `ad`. L'export se copie dans
`$RUN/trace/`, avec la commande qui l'a produit et la fenêtre `horodatage_debut`–`horodatage_fin`.
C'est la seule pièce que l'opérateur n'écrit pas — et celle sans laquelle le run n'est qu'une
parole.

### 1.6 Que le contexte du candidat soit mesuré, et lu dans la trace

Mesuré le 2026-10-15, après le premier run : une session peut mourir **au plafond de son contexte**, et
le serveur **tronque alors en silence** (un prompt de ~40 000 jetons rend `prompt_eval_count` =
16 386, `ollama ps` annonce `CONTEXT 32768`). Aucune pièce du run ne le montrait : ni la trace du
client, qui compte ce qu'il a *envoyé*, ni le reçu.

Le second run change de client : **la session opératrice est une session Freebuff**, à modèle hébergé.
Le plafond n'est donc plus celui du serveur local, et la mesure n'est plus une sonde mais une lecture,
faite **après** le run, dans ses propres messages :

```text
sqlite3 -readonly ~/.config/freebuff-desktop/projects/<projet>-<uuid>/desktop-v2.db "
  select m.seq, json_extract(m.metrics_json,'$.context.windowTokens'),
                json_extract(m.metrics_json,'$.context.compactionThresholdTokens'),
                json_extract(m.metrics_json,'$.context.usedTokens')
    from messages m where m.thread_id='<thread>'
     and m.metrics_json like '%windowTokens%';"
```

Relevé dans la base de Freebuff le 2026-10-15 : **la fenêtre annoncée varie d'un message à l'autre
pour un même modèle** (1 048 576, 1 000 000, 500 000, 262 144, 131 072 selon le moment), avec des seuils
de compaction de 320 000, 160 000 ou 88 000. Il n'y a donc pas de constante à citer : la fenêtre du
run se lit **dans les messages du run**. Le chiffre va au reçu, en `--limite`, à côté du modèle.

**La compaction est un événement du run, pas un détail.** Sur ce poste, 124 messages portent une
compaction et `parts_json` en contient 158 parts (`"kind":"compaction"`) : au seuil, le client réécrit
son propre contexte. Une trace qui ne dit pas qu'une compaction est survenue ne dit pas ce que la
session avait sous les yeux — c'est la matière de F9, et l'export du §1.5 la porte. Un `usedTokens`
au-dessus du seuil de compaction, dans les messages du run, se dit en limite.

**Si un run revient à un modèle local**, la sonde et le remède restent valables, et éprouvés le
2026-10-15 : sur ce poste le contexte par défaut est **32 768**, identiquement pour un 36B et pour un
9B (aucun modèle de la bibliothèque ne porte de `num_ctx` dans sa couche `params`), et un modèle dérivé
des mêmes poids rend 131 072 sans dupliquer un octet de poids ni changer le gabarit :

```text
printf 'FROM qwen3.6:35b\nPARAMETER num_ctx 131072\n' > /tmp/Modelfile-131k
ollama create qwen3.6-131k -f /tmp/Modelfile-131k   # ollama ps -> CONTEXT 131072
```

Ce que ce remède ne prouve pas : que le **client** du run laisse passer cette fenêtre (il peut poser
son propre `num_ctx`) — c'est une sonde à faire au client, pas au serveur, avant d'ouvrir.

## 2. Ce qui se remet mot pour mot

### 2.1 Le texte

Entre les deux lignes de garde, et rien d'autre :

```text
<<<DEMANDE
Read the project-memory skill from /home/giak/projects/aidd-device-work/2026-10-15-133423-promesse-memoire-avant-ecriture/framework-origin/plugins/aidd-context/skills/02-project-memory/SKILL.md and use it on this repository. It has no project memory yet.
>>>DEMANDE
```

Le texte ne se retape pas : il se copie du fichier gelé. **Deux empreintes le disent, et il ne faut
pas les confondre** :

- **le fichier de la demande gelée** — `sha256` `dce9e131…` : c'est la seule que le reçu porte, sous
  `demande.sha256` (le reçu nomme le fichier, jamais un texte) ;
- **le texte lui-même**, les deux lignes de garde retirées — `sha256` **`832036f7…`**, 254 octets, sans
  saut de ligne final. C'est ce chiffre-là qu'on compare à ce que la session a reçu.

```text
CAS=docs/device/CASES/2026-10-15-133423-promesse-memoire-avant-ecriture.request.md
T=$(sed -n '/^<<<DEMANDE$/,/^>>>DEMANDE$/p' "$CAS" | sed '1d;$d')
printf '%s' "$T" | sha256sum           # 832036f7… — 254 octets, le texte qu'on colle
printf '%s' "$T" > /tmp/texte.txt      # le même, sans saut de ligne final
```

Le `printf '%s'` n'est pas décoratif : sans lui, le shell garde le saut de ligne de la dernière ligne
et le **même** texte rend `2ddc2451…` pour 246 octets. Les deux chiffres sont vrais, ils ne mesurent
pas la même chose.

*Rectifié le 2026-10-15 au soir : cette page citait `a3121f7f…` comme empreinte du texte, « celle que
le reçu porte ». Vérification faite, elle ne correspond à rien — 28 candidats essayés (texte nu,
guillemeté, gardé, en `LF` ou `CRLF`, `texte_verbatim` du JSON, ancien texte relatif, blobs
versionnés), aucune correspondance — et le reçu ne porte de toute façon aucune empreinte de texte.*

L'ancien gel, celui du premier run, portait `4f7c189c…` pour le même fichier. La session est **neuve**,
ouverte dans `$W/terrain` et avec sa **racine de projet** posée là aussi (§4) : c'est elle qui décide où
tombent les chemins relatifs de la skill, pas le répertoire courant.

Le geste exact dépend du client, et n'a pas été mesuré ici — ce qui est mesuré est la conséquence :
tant que la racine de projet du client n'est pas `$W/terrain`, les écritures relatives de la skill
n'y tombent pas. Les deux clients constatés sur cette machine nomment cette racine : Claude Code
comme `CLAUDE_PROJECT_DIR` (`hooks/update_memory.js` s'y ancre), Freebuff Desktop comme un projet,
un par base (`~/.config/freebuff-desktop/projects/<projet>-<uuid>/`, spec §5.1). Ouvrir la session
ailleurs, avec la copie seulement à portée du shell, n'est donc pas tenu pour équivalent.

### 2.3 Ce qui ne part jamais, et le budget

`CASES/2026-10-15-133423-promesse-memoire-avant-ecriture.expected.json` (**14 879 octets**, `sha256`
**`e32e420c…`**, l'empreinte que le gel porte ; `d9b4ee01…` était l'état d'avant les rectifications,
que le [journal](../../../trace.md) date) reste chez le dispositif — ni relayé, ni résumé, ni laissé
lisible par la session. Une
session qui a vu l'attendu mesure sa capacité à lire un attendu : le reçu porte `attendu_vu: oui` et
le cas se conclut `non concluant`. Cette page et le [journal](../../../trace.md) ne partent pas non
plus.

**Trois échanges au plus** : le premier porte la demande (§2.1), les deux suivants sont les réponses
figées (§2.2). Un run qui épuise les trois sans avoir rendu son tableau se conserve tel quel, se
conclut `non concluant`, et le reçu nomme l'échange qui l'a épuisé.

```text
# le juge, ensuite, sur le reçu SEUL :
node "$H" compare --run "$RUN" --case "$CAS" \
  --difference "<ce que le produit fait>" \
  --phrase "<au vu de l'attendu écrit, le produit fait X ; l'attendu disait Y>" \
  --verdict conforme|ecart|non concluant --limites mord|ne mord pas|non évaluable
```

1. **`collect`** copie verbatim le produit sous `raw/<cas>/` et écrit son manifeste : `sha256`,
   taille, `birth` de chaque fichier, et la source absolue. Le produit attendu est la table
   `Write to` de `references/memory-destinations.md`, donc `terrain/aidd_docs/` — tout le reste est
   hors produit (demande §6), même écrit dans le répertoire de travail.
   Il refuse : un dossier déjà collecté (deux collectes font deux produits), un lien symbolique
   (une sortie du répertoire de travail n'est pas un produit), une copie dont le `sha256` diffère,
   un `--from` vide.
2. **`last-message.md`** s'écrit après lui, à la main : le dernier message de la session, verbatim.
3. **`trace/`** reçoit l'export du §1.5 et sa commande.
4. **`receipt`** s'écrit à chaud, pendant le run, et refuse d'écraser un reçu existant : un reçu
   reconstruit le lendemain est un témoignage, pas un reçu. Il exige le gel, le manifeste et
   `faits.json` ; il remesure les quatre arbres ; il vérifie les quatre falsificateurs du §5.
5. **`compare`** appartient au juge, pas au run : il travaille sur le reçu seul, ne voit pas la
   session, et écrit `output.json` — l'attendu, le produit brut, la différence, la phrase de
   verdict, les limites, et les attendus écartés comme non testables.

### 3.2 Les quatre falsificateurs, et ce que le harnais ne lit pas

Un seul suffit à faire tomber le run, et le verdict suit la preuve (spec §7) :

| Condition (§5) | Ce qui la fait mordre |
| --- | --- |
| 1 — naissance | le `birth` d'un fichier produit est antérieur au gel |
| 2 — trace | la trace machine ne porte aucun échange dans la fenêtre du run |
| 3 — arbre | le produit existe alors que le `porcelain` de `travail` est inchangé |
| 4 — empreinte | le produit est identique à un fichier déjà présent avant le run |

La condition 2, le harnais **ne peut pas** la lire : il l'écrit lui-même en limite (« le harnais ne
lit aucune des trois sources du §5.1 »). La pièce (1) est attestée par l'export, pas par ce script.

### 3.3 Le plafond du verdict

- naissance **et** trace **et** arbre → le cas peut être `conforme` ou `écart` ;
- trace et arbre, sans la naissance → verdict possible, la limite dite dans le reçu ;
- sans naissance ni trace → `non concluant`, quoi que dise l'opérateur ;
- cloisonnement rompu → `non concluant`, dans tous les cas.

Le reçu porte ces limites, et la phrase de verdict — « au vu de l'attendu écrit, le produit fait X ;
l'attendu disait Y » — n'attribue ni faute ni mérite : elle compare.

## 4. Ce que cette conduite ne fixe pas

- **La session** : application, modèle, identifiant — paramètres du run, relevés au moment où ils
  existent, jamais choisis ici.
- **L'horodatage et la révision du dispositif** : mesurés au run (§1.3), pas écrits d'avance.
- **Les interdits du §7 de la demande — arbitrés le 2026-10-15 (ADR-015), plus `OPEN`.** Le §5 garde
  sa lettre : le texte remis est ces deux lignes et rien d'autre. Les interdits ne sont donc pas dits ;
  ils doivent être **structurellement** vrais à l'ouverture, et c'est ce qui a été mesuré. À la
  révision sous test, aucune étape de la skill n'écrit hors du projet : `references/tools.md` et
  `hooks/update_memory.js` visent `CLAUDE.md`, `AGENTS.md`, `.github/copilot-instructions.md` et
  `aidd_docs/**` — tous des chemins **relatifs au projet** — et le script ne stage rien quand la skill
  l'appelle (le `git add` n'appartient qu'au hook automatique). Ce qui a réellement fait sortir un
  agent du cadre, deux fois le 2026-10-15, n'est pas un manque de paroles mais la résolution d'un
  chemin relatif par le client contre **sa** racine de projet ; aucun interdit énoncé ne l'aurait
  empêché. Conséquence à l'ouverture : la racine de projet de la session est posée sur `$W/terrain`.
  Le seul interdit qui reste non structurel est « ne pas lire `CASES/` » : rien dans la demande ne l'y
  invite, et le reçu le mesure (`cloisonnement.attendu_vu`).
- **Le verdict** : personne ne le connaît avant le run, et cette page ne l'anticipe pas.
